Provider Abstraction Design

A rough prototype, not final code — the actual STT/Translation/TTS provider interfaces, sized to react to. Reflects the real shapes from ticket 04's research and fits ticket 05's decided pipeline (LLM-hybrid segmentation, TOKEN-mode TTS with explicit flush).

Design convergence from ticket 12's prior-art research: Pipecat, LiveKit, and Vocode independently arrive at the same swap point — "one streaming method, in: raw input, out: an async stream of typed events." Below follows that shape. Also per that research: this interface deliberately does not try to also cover the Realtime API (ticket 03) — LiveKit keeps those as separate object families on purpose.

Design choices worth flagging

  • Protocol, not ABC. Structural typing (PEP 544) — a test double for provider-boundary tests (ticket 10) just needs to satisfy the shape, no inheritance required. Fits "targeted tests on... provider boundaries."
  • is_final vs. speech_final both survive onto TranscriptSegment, not collapsed into one flag — the orchestrator's LLM clause-check (ticket 05) needs is_final segments to check for early completeness, while speech_final stays the independent fallback boundary.
  • Capability-declaration dataclasses (STTCapabilities) — LiveKit's pattern from ticket 12, in case future providers don't support the same feature set (e.g. no word timings, no interim results).
  • An empty final STT result is not an error — TranscriptSegment.is_empty is a valid outcome (correctly transcribing silence/noise as nothing, ticket 11's noise-rejection test), distinct from ProviderError which is for actual failures.
  • Translation doesn't decide segmentation — translate() takes one already-segmented unit; the LLM-hybrid boundary logic lives in the orchestrator (ticket 05), not duplicated into this provider layer.

Self-review honest gaps, per your question

The real gap: deepgram_stt.py's stream() doesn't actually work as written. It defines _pump_audio() but never schedules it to run, registers an @connection.on("Results") callback but never drains those results into anything the caller can async for over, and has no yield statement at all. I labeled that section "illustrative," but that's underselling it — the missing piece is precisely the hardest and most important part of the whole class: bridging Deepgram's callback-based SDK into a real async generator, concurrently with pumping audio in. The actual shape needed: an asyncio.Queue, the "Results" callback does queue.put_nowait(segment), _pump_audio() runs as a concurrent asyncio.create_task alongside a loop that does while True: yield await queue.get(). That's real implementation work I deliberately didn't write here (out of scope for a prototype per the map's Notes — implementation happens as a normal build afterward) — but I should have said so explicitly instead of just marking it "illustrative" and moving on.
Smaller, not real problems, worth naming anyway: the Protocol methods are declared def ... -> AsyncIterator[...], not async def — that's intentional and correct (calling an async generator function is itself synchronous; only advancing it is awaited), but it can read as a typo to someone unfamiliar with the pattern and deserves a comment in the real code. Also a minor naming inconsistency across the event types (TranscriptSegment vs. TranslationChunk vs. TTSText/TTSFlush) — cosmetic, but worth picking one noun before this gets implemented for real.

When does a new phrase "start" vs. "continue"? answering your question

Phrase start has no separate time parameter of its own — it's Deepgram's SpeechStarted event, which fires the instant VAD detects audio resuming after silence. Since capture never stops (ticket 05), whatever comes right after a boundary is cut automatically becomes the next phrase — there's nothing extra to configure.

Phrase end / continue does have explicit time parameters, both set in the prototype above: endpointing=300 (300ms of silence triggers speech_final — ticket 04's research recommended 300-500ms for natural conversational pauses, vs. Deepgram's 10ms default meant for fast chatbot-style turns) and utterance_end_ms=1000 (a 1000ms backup signal, independent of endpointing, for cases where a pause doesn't cleanly register).

The LLM-hybrid check (ticket 05) has no time parameter at all — it's event-driven, not interval-driven: it fires on new is_final segments, judging clause-completeness from the text itself, debounced to one check in flight at a time. Honest gap: ticket 05 never pinned an exact minimum spacing between checks if Deepgram emits final segments faster than the LLM can judge them — that's a real open tuning parameter, not yet a hard decision.

Multiple voices — does Deepgram handle that? answering your question

Yes — Deepgram supports speaker diarization via a diarize=true parameter, which tags each word with a speaker index (0, 1, 2...) based on voice clustering. It doesn't identify who anyone is, just separates distinct voices in one audio stream. Caveat: this wasn't part of ticket 04's verified primary-source research (that was scoped to endpointing/interim-results/audio-format), so treat this as general knowledge, not a confirmed spec.

This exposes a real gap: the current design implicitly assumes one active speaker per capture stream — nothing in ticket 05's architecture or this prototype accounts for two people sharing one microphone/connection. Given the brief's requirement is a language-pair toggle with source/target transcripts (not explicitly multi-party diarization within one audio channel) and the 15-20hr budget, the pragmatic default is to keep treating this as out of scope — one active speaker per capture session, with two-way conversation handled by each party having their own mic/session rather than diarizing a shared feed. Flagging this rather than silently assuming it — worth an explicit "yes, out of scope" or opening it as a real decision if that assumption is wrong.

Adding diarization — bigger than it looks per your feedback

You're right to want this, and it's worth naming precisely why: the brief's stability benchmark says "sustain a 5-minute back-and-forth conversation" — two people alternating, in two languages. The current design (ticket 05) implicitly assumed a fixed session-wide translation direction (pick "English → Spanish" once, translate everything that way) — which doesn't actually support true back-and-forth without someone manually flipping a toggle between every turn. Diarization plus per-segment language detection is a real fix for that, not scope creep.

Fixed speaker→language mapping

User calibrates at session start ("Speaker A speaks English"). Simple, but fragile — Deepgram's speaker index (0, 1...) is just voice clustering, nothing guarantees it stays mapped to "the English speaker" reliably.

Per-segment language detection recommended

Detect which of the two configured languages each segment is spoken in, translate to whichever one it isn't. Works cleanly because the pair is always exactly 2 languages — no speaker-identity calibration needed at all. speaker (from diarization) is then used only for UI transcript labeling and keeping each person's TTS voice consistent across the session — not for deciding translation direction.

Scope call: Cascade mode only, not Realtime mode. Deepgram natively supports diarizing a shared feed; OpenAI's gpt-realtime is built around a single input stream with no equivalent multi-party lever. Forcing symmetry would mean guessing at unresearched Realtime API behavior for uncertain payoff. Recommending this becomes a deliberate, named difference between the two modes in the comparison write-up — cascade's "more control" vs. realtime's "less control" (the brief's own framing) made concrete with a real example, not just asserted.
