Wave 0 frontier — start now, parallel

Ticket 1 — Realtime mode: voice-in/voice-out MVP

right-sized · ~2 hrs
Depends on: none
Backend

POST /api/realtime/session mints an ephemeral client secret server-side via OpenAI's POST /v1/realtime/client_secrets. Session instructions steer gpt-realtime to translate (turn-based) for a hardcoded EN↔ES pair.

Frontend

Minimal shell: "Connect" button → mic permission → RTCPeerConnection direct to OpenAI (SDP offer/answer, data channel oai-events), pc.ontrack → audio element. No dual-column UI yet — that's Ticket 3.

Acceptance criteria & API notes
  • Speaking English produces spoken Spanish, and vice versa, using literally gpt-realtime (brief calls it "required").
  • The real OpenAI API key never reaches the browser — only the short-lived ephemeral secret.
  • Speech-end → first-audio-out feels well under 1.5s by ear (formal instrumentation is Ticket 6).
  • Denying mic permission shouldn't crash the tab (graceful UX is Ticket 7).

Contract: browser owns the RTCPeerConnection directly once the ephemeral secret is issued — backend is off the audio path from that point on.

Ticket 2 — Cascade mode: end-to-end MVP with provider abstraction

right-sized but large · ~4–5 hrs includes provider contract tests
Depends on: none (parallel with Ticket 1)
Backend

providers/base.py — STTProvider / TranslationProvider / TTSProvider as Protocol, structured ProviderError. DeepgramSTTProvider (WS, endpointing=500, real async-generator bridge over the callback SDK — the wayfinder's own prototype left this sketched, not wired), OpenAITranslationProvider, ElevenLabsTTSProvider (WS stream-input, TOKEN mode, explicit flush at boundaries). Orchestrator: STT → single-utterance segmentation (Deepgram speech_final only — LLM-hybrid is Ticket 5) → translation → TTS, one full-duplex WebSocket per session.

Frontend

AudioWorklet capture (Float32→Int16 scale-and-clamp, ~20–40ms frames), minimal unstyled UI (two text blocks), Web Audio API buffer scheduling for gapless raw-PCM TTS playback.

Why this ticket is the thickest — and why it isn't being split

Considered splitting into "text pipeline" (STT→Translation) + "add TTS" — rejected because the TTS-only remainder (~1–1.5 hrs) would be too thin to justify its own orchestration overhead. The thickness matches the architecture's own inherent complexity (this pipeline is "meaningfully more engineering" than Realtime mode, per the wayfinder itself), not a slicing failure.

Acceptance criteria & API notes
  • Speaking English produces a live English transcript, a live translated Spanish text block, and spoken Spanish audio out (hardcoded EN↔ES, single speaker/direction).
  • STT/Translation/TTS calls go only through the Protocol interfaces — swapping ElevenLabsTTSProvider should touch one file.
  • Silence (empty final STT) doesn't raise a ProviderError — it's a valid is_empty=True outcome.
  • Provider contract tests pass for all three providers: happy path + every documented failure → ProviderError mapping (pytest + pytest-asyncio, hand-mocked SDKs, no live network calls).
  • Streaming throughout — no full-utterance blocking at any stage.

Contract: one full-duplex WebSocket per session. Client → start_session (language pair), binary PCM frames. Server → source_transcript/target_transcript (with segmentId, isFinal), segment_boundary (trigger: llm or Deepgram signal — always Deepgram for now), tts_audio_meta + binary audio frame. Translation provider: OpenAI.

Ticket 3 — Unified workbench shell: mode toggle, language selector, dual-column transcripts

right-sized · ~2 hrs
Depends on: Ticket 1, Ticket 2
Backend

Thin — extend the session endpoint and start_session message to accept a real (not hardcoded) language pair.

Frontend

Replace both minimal UIs with the winning layout (ticket 09, split dual-column variant): navbar with mode tabs + language selector + connection-status badge; dual-column transcript panes; mic control with level meter. Acceptance criteria

  • Language selector defaults to and supports English ↔ Spanish.
  • Both transcripts stream live in both modes, appended not re-rendered per token.
  • Mode-specific transport code (WebRTC vs. WebSocket) never leaks into shared UI components.
  • Connection-status badge shows "Connected" once a session is live.

Wave 2 parallel — 3 tickets, at the ask-first ceiling

Ticket 4 — Cascade: diarization + per-speaker voice

right-sized · ~1.5–2 hrs
Depends on: Ticket 2, Ticket 3
Backend

diarize=true + detect_language=True on Deepgram. Per-segment translation-direction resolution (of the 2 configured languages, detect which one, translate to the other — no manual toggle). Consistent speaker → ElevenLabs voice_id mapping. speaker threaded through all transcript/TTS messages.

Frontend

Per-speaker color-coded badges in both transcript panes, matching each speaker's distinct TTS voice.

Acceptance criteria & open caveats
  • Two people alternating in different languages each get a consistent speaker badge and correct translation direction, no manual toggle.
  • Each speaker is spoken back in a distinct, consistent TTS voice.
  • Cascade-only capability — a deliberately named asymmetry for the write-up.

Two caveats to verify while building, not yet resolved: whether Deepgram's detect_language can be constrained to the 2-language candidate set, and how a segment spanning a mid-utterance speaker change behaves.

Ticket 6 — Latency instrumentation, both modes

right-sized · ~2 hrs
Depends on: Ticket 1, Ticket 2, Ticket 3
Backend (Cascade only)

Timestamp capture at each stage (speech_end → translation first token → translation complete → TTS first byte → client-reported playback start). Clock-sync offset re-run every 30s and after reconnects.

Frontend

Cascade: live per-stage running-total table vs. 2s target. Realtime: end-to-end number only (purely client-side — backend has no visibility once the ephemeral token is issued) vs. 1.5s target.

Acceptance criteria & API notes
  • Cascade shows a live 5-stage latency breakdown per segment during the session.
  • Realtime shows end-to-end only — an intentional asymmetry, not a bug.
  • Clock offset recomputes every 30s, not just once.
  • Numbers are genuinely measured — a real network hiccup visibly inflates that segment's latency.

Contract: latency message stages: speech_end (0), translation_first_token, translation_complete, tts_first_byte, playback_start (the brief's actual benchmark number), each cumulative ms since speech_end. Realtime mode sends no latency message at all.

Ticket 7 — Error handling & session resilience

right-sized, merged · ~3–3.5 hrs includes retry/circuit-breaker tests
Depends on: Ticket 1, Ticket 2, Ticket 3
Backend

Bounded retries per failure mode (rate limit 2×, timeout 1×, empty translation 1×). 5-consecutive-failure circuit breaker → hard "unavailable" state. Backend↔provider reconnect (500ms→1s→2s backoff) without tearing down the browser↔backend socket; in-flight segment dropped+logged. Browser↔backend: short grace-window reconnect, else session ends. Memory hygiene: per-segment buffer release, WS backpressure.

Frontend

Mic-denied blocking banner with working retry (not a reload). Non-blocking toast for rate-limit/timeout. Silent drop for empty results. Connection badge turns amber ("Reconnecting…") during a reconnect attempt.

Why this merges the wayfinder's tickets 10 + 13

Ticket 13's own answer found 2 of its 3 sub-questions already solved by earlier decisions (clock drift reuses Ticket 6's resync design; audio playback drift is a non-issue given the segmented architecture) — the only genuinely new stability work is reconnection + memory hygiene, which explicitly reuses this ticket's circuit breaker. Splitting them would produce two overlapping small tickets over the same failure-handling surface.

Acceptance criteria
  • No single provider failure ever ends the session — only that one segment.
  • 5 consecutive failures trips the circuit breaker with an explicit "interpretation unavailable" state.
  • Denying mic permission shows a blocking banner with working retry.
  • Killing Deepgram/ElevenLabs mid-session shows amber "Reconnecting…" and recovers transparently.
  • A brief browser↔backend blip recovers; a longer one ends the session cleanly, not a hang.
  • No automatic runtime provider fallback exists — by design.

Wave 3

Ticket 5 — Cascade: LLM-hybrid segmentation upgrade

right-sized · ~2–2.5 hrs includes segmentation race test
Depends on: Ticket 2, Ticket 4
Backend

Async LLM clause-check side-channel races independently against Deepgram's speech_final/UtteranceEnd — whichever fires first wins, capture never pauses. Debounced to one check in flight per speaker (needs Ticket 4's speaker tracking). Configurable mode: hybrid race (default) vs. LLM-priority (Deepgram's speech_final ignored, UtteranceEnd stays as a hard ceiling so a segment can never hang).

Frontend

Surfaces segment_boundary's trigger reason for debugging; a dev-facing toggle/query-param for segmentation mode is enough (no polished settings UI needed).

Acceptance criteria & API notes
  • A natural mid-thought pause isn't cut prematurely (endpointing=500ms, bumped from research's original 300ms).
  • A complete, grammatically finished clause gets translated and spoken before the speaker pauses, when the LLM check wins the race.
  • Worst case, the segment still completes via Deepgram's fallback — no segment ever hangs, in either mode.
  • Both segmentation modes are exercisable for Ticket 9's empirical A/B comparison.

Called out by the wayfinder as "the single most complex custom logic in the system" — kept as its own ticket with dedicated test coverage on purpose.

Wave 4

Ticket 8 — Quality validation suite

right-sized · ~2.5–3 hrs
Depends on: Tickets 1, 2, 3, 4, 5, 6, 7 — exercises the full app
Backend

Shared test dataset (~15–20 everyday items + longer multi-clause + multi-turn snippets, domain-agnostic), TTS-generated audio fixtures (EN/ES). WER via jiwer, asserted below threshold. LLM-as-judge translation-quality scorer explaining what's wrong, not just a score. Process-memory sampling (psutil) around a scripted 5-minute run.

Frontend / test-infra

Playwright E2E with Chrome's fake-mic device flags, exercising the real capture→STT→translation→TTS path in both modes. Noise-rejection fixture asserting no spurious transcript. Supplementary manual-tier: a handful of real (non-TTS) recordings across varied mic conditions.

Why this is vertical, not a horizontal "write tests" slice

Component-level tests (provider contracts, segmentation race, retry/circuit-breaker) are deliberately embedded in Tickets 2, 5, and 7 where that logic gets built. This ticket is scoped to system-level validation — it produces an actual data artifact (WER%, LLM-judge report) that Ticket 9 directly consumes.

Acceptance criteria
  • WER regression test passes below threshold for both EN and ES, fails loudly on regression.
  • Playwright fake-mic E2E passes for both modes within a time budget, using the real (unmocked) path.
  • Noise-rejection fixture produces no spurious transcript.
  • LLM-as-judge produces an actionable per-item report for the same corpus through both modes.
  • Same dataset runs through both modes — apples-to-apples for Ticket 9.
  • Process-memory sample shows no unbounded growth across a simulated 5-minute run.
