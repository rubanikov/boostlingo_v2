Latency Instrumentation Design

Three decisions: what gets timestamped per mode, how client/server clocks reconcile, and what actually shows in the UI. The honest headline: the two modes can't get symmetric instrumentation, and that asymmetry is itself worth showing, not hiding.

Clarifying the original question: there's no distinct "mic capture end" event to timestamp — capture never stops (ticket 05's concurrency answer). The only meaningful "end" moment is the segmentation boundary firing (the LLM clause-check verdict or Deepgram's speech_final/UtteranceEnd fallback) — that is "speech end" for measurement purposes.
question 1 of 3

What gets timestamped, per mode?

Cascade — rich, per-stage

The backend owns every stage, so it can timestamp all of them: segment boundary fires (t_speech_end) → translation first token → translation complete → TTS first byte → client reports playback start. Full breakdown, all server-computed.

Realtime — coarse, end-to-end only

The backend is off the audio path (ticket 03) and everything happens inside one opaque model call — there's no sub-stage to see. Only two measurable points exist: the data-channel's speech-stopped signal, and the browser's audio element starting to play. This isn't a shortcoming to paper over — it's a direct, visible consequence of the architecture, and a genuinely useful data point for the brief's controllability comparison.

Conversation end vs. segment boundary answering your question

Worth separating two different "end" concepts explicitly: session end is the user pressing the stop/end button — terminates the connection, one-time, out of scope for this ticket. Segment boundary is what this whole ticket measures — it recurs continuously throughout a session, once per spoken chunk, and is what the UI shows as a new line/block in the transcript panes (both source and target) each time it fires — confirmed, that's exactly ticket 05's "partial transcript display" design.

Correcting one detail: it's not exclusively the LLM that decides a segment boundary. It's a race between two independent signals (ticket 05) — the LLM clause-check verdict (judging the transcript text itself) and Deepgram's own audio-based endpointing (speech_final/UtteranceEnd, a silence-pause detector) — whichever fires first for a given stretch of speech wins. In practice, for short simple utterances Deepgram's fast endpointing (300ms silence) will often win the race on its own; the LLM verdict mainly "wins" when it catches a complete clause before a natural pause would show up — e.g. partway through a longer multi-clause sentence. So "the user pauses, waiting for translation" is usually Deepgram detecting that pause, with the LLM check as the early-cut path for longer utterances specifically.

Your 300ms concern, and the toggle request real issue, worth answering carefully

You're right that 300ms is genuinely too aggressive for "thinking pauses" — someone pausing mid-thought to find the right word easily exceeds that. But I wouldn't remove Deepgram's fallback entirely and let the LLM decide alone: it exists specifically as a guaranteed-progress safety net (ticket 05) — if the LLM check ever fails to fire a "complete" verdict (a malformed check, a rambling non-clause-shaped utterance, a slow API response), a pure LLM-only design would just hang with no boundary ever firing. That's the actual risk being traded off, not a preference for Deepgram over the LLM.

Two changes I'd make instead, both addressing your concern directly:

  • Bump endpointing from 300ms to 500ms — the top of ticket 04's own researched range for natural conversation, not a new number. Directly reduces premature cuts during thinking-pauses, zero added risk.
  • Add the toggle you asked for — a configurable segmentation mode: today's hybrid race (current default) vs. an "LLM-priority" mode where the LLM verdict is preferred and Deepgram's fast speech_final is ignored, but the slower UtteranceEnd (already in the design, 1000ms+) stays as the hard fallback so there's still a guaranteed ceiling on how long a segment can hang open. Genuinely useful for testing, and strengthens the comparison write-up with real empirical behavior instead of just asserted reasoning.

This is really ticket 05's territory (segmentation architecture), not this ticket's — I'll write it up as an amendment there, the same way ticket 06's diarization addition got folded back in, rather than silently absorbing it into latency instrumentation's scope.

question 2 of 3

Clock synchronization

Recommendation: one-time offset at session start, all "official" numbers computed server-side in one clock frame. A quick ping/pong at connection time (client sends its clock, server echoes with its own, client derives an NTP-style offset with ±RTT/2 uncertainty — plenty precise for a latency display, not a scientific benchmark). The client then reports "playback started at client-time T" back to the backend, which converts that using the stored offset and computes the full per-stage breakdown itself — so every number the UI shows was computed in a single consistent clock, not stitched together from two clocks per message.
Realtime mode needs none of this — an accidental upside of the backend being off the audio path (ticket 03): both measurable timestamps (speech-stopped signal, audio-playing state) happen in the same browser clock, no client/server reconciliation required at all.

Disadvantages, and what a network issue does to this answering your question

Real disadvantage: a one-time offset can go stale over a long session. Computer clocks drift — gain or lose milliseconds over time — and the brief's own stability benchmark is a 5-minute session, long enough for drift to actually accumulate into visible error by the end. Amending the recommendation: re-run the ping/pong every 30s (confirmed), not purely once at session start, and always after any reconnect (ties directly into Stability: reconnection, drift, memory, ticket 13 — which should own the reconnect trigger, this ticket owns re-running the offset calculation when that trigger fires).

Network issue mid-segment (your specific question): a transient hiccup during a segment's processing shows up as an inflated stage latency in the measurement — that's the instrumentation doing its job correctly, not a flaw to fix. A dropped/delayed latency message itself just means that one number doesn't appear in the UI for that segment — acceptable graceful degradation, since these are diagnostic-only messages, not on the actual translation pipeline's critical path (losing one doesn't break interpretation, only the diagnostic display for that data point). A network issue severe enough to actually drop the WebSocket connection is the harder case ticket 13 owns — and per the point above, offset resync needs to be part of that reconnect flow, not assumed to still be valid.

Also a real disadvantage even without drift or reconnects: the offset math assumes a roughly symmetric network path (upload and download latency similar) — on an asymmetric connection (common on many home/mobile networks) the one-shot offset carries a bias for the entire session. Periodic resync partially mitigates this too, since it gives more samples to average, though it doesn't eliminate the assumption itself.
