Epic narrative

As the single developer/researcher running the AI Interpreter Workbench as a lab,
I want every audio, turn-taking, segmentation, denoise and transcript-check processing step exposed as a selection in an in-app Tuning panel, applied both at session start and live mid-session, and measurable against a noisy corpus,
so that I can answer "does this processing step improve WER, judge score or latency?" with a number per configuration instead of a guess.

Tier 1–2 must-have Tier 3–4 should-have Tier 5–6 first to cut

Fingerprint: a short, stable hash of the canonical TuningConfig JSON, computed by shared code so UI, backend and harnesses derive the same string. It is the join key between a run and its numbers.

Story 1 — Tuning panel & config plumbing Tier 1

As the researcher, I want a Tuning panel in WorkbenchPage that owns every existing knob and pushes it into the session at start and live mid-session, so that I can change one variable at a time without editing .env or restarting the server.

1.1Panel is the single inventory. Sections per processing step — Microphone constraints, Denoise chain, Turn detection, Segmentation, Transcript check, Models — every knob in decision 5 for the current mode appears. No knob the app reads is settable only via .env or a query param. 1.2Realtime start-of-session apply. Set server_vad + silence_duration_ms=300 → Connect → POST /api/realtime/session body carries them → backend puts them under session.audio.input.turn_detection. 1.3Unset stays unset. A field left at "Provider default" is absent from the outbound OpenAI payload (existing _turn_detection() idiom). 1.4Cascade start-of-session apply. llm_priority + endpointing=300 ride inside start_session; the Deepgram connection URL reflects them under test. 1.5Realtime live apply. Change silence_duration_ms → Apply → session.update sent on the oai-events data channel; session not torn down; panel shows "applied". 1.6Cascade live apply, non-connection-level. e.g. segmentation mode → new WS control message; Deepgram not restarted; effective for the next segment. 1.7Cascade live apply, connection-level. endpointing/utterance_end_ms/diarize/model → deliberate Deepgram reconnect; every frame sent before/during/after appears in the transcript — no frame dropped, no segment lost. 1.8Persistence. Reload → same values (localStorage); nothing stored server-side. 1.9Presets. Built-ins "Provider defaults", "Tuned turn-taking", "Max denoise" set every knob in one action; user-saved presets survive reload. 1.10Export / import. Export gives the TuningConfig JSON; importing it restores exactly that config. 1.11Backend defaults still apply. Fresh browser → session uses .env-derived defaults and the panel displays those values, not blanks. 1.12Fingerprint is visible. Displayed in the panel; changes when any knob changes; identical for configs differing only in field order. 1.13Mode-scoped. Switching Realtime ↔ Cascade shows only that mode's knobs and never silently applies the other mode's values.

Story 2 — Noisy corpus & per-config benchmark Tier 2

As the researcher, I want a noisy version of the 33-item corpus and harnesses that run any TuningConfig end to end, so that every knob claim is backed by WER, judge score and latency keyed by fingerprint.

2.1Noise synthesis. Per item: babble (several overlaid TTS speakers, same + other language), street, fan/white — each at 20/10/5 dB SNR — mono 16-bit 16 kHz; audio git-ignored, script + SCRIPT.md committed. 2.2Cascade STT sweep. Extended stt_replay.py: one row per (item, condition, SNR) with WER + fingerprint. 2.3Realtime sweep. realtime-quality-capture.mjs applies the config in the UI before connecting; items + envelope carry the fingerprint. 2.4Report. run_realtime_quality_report.py: every row + summary carry the fingerprint; WER, judge acceptance, E2E latency. 2.5Clean baseline always shown beside noisy conditions. 2.6Comparison output. ≥2 fingerprints → paste-ready markdown table, one row per fingerprint; COMPARISON.md gains a tuning-config section. 2.7Added latency attributed separately from provider latency ("this stage cost N ms"). 2.8Real-recording set self-skips with a friendly message and exit 0 (as run_real_audio_report.py).

Story 3 — Client-side denoise stages Tier 3

As the researcher, I want browser constraint toggles, an RMS noise gate, RNNoise and OpenAI input noise reduction selectable per session, so that I can measure whether live-path denoising improves WER.

3.1Mic constraints. EC/NS/AGC off in the panel → getUserMedia called with exactly those values in either mode. 3.2RMS gate parameters. threshold −45 dBFS, hold 200 ms, attack 5 ms, release 80 ms, attenuation 12 dB → sub-threshold audio attenuated by 12 dB (not muted), above passes unchanged; attenuation = full mute → silenced. 3.3Gate is live-adjustable without reconnecting. 3.4RNNoise. Mic audio passes through RNNoise before the transcript path in both modes; a clean clip still yields a non-empty transcript (48 kHz / 480-sample resampling doesn't destroy the signal). 3.5Realtime client DSP plumbing. WebRTC track carries processed audio; mic-mute-during-reply still mutes the track actually being sent. 3.6OpenAI noise reduction. off / near_field / far_field sent under session.audio.input.input_audio_noise_reduction; "off" follows the unset-means-provider-default rule as stated in the panel. 3.7Measured, not asserted. Each stage has ≥1 benchmarked fingerprint on the noisy corpus with its WER delta vs the same config with the stage off.

Story 4 — Transcript-check LLM stage Tier 4

As the researcher, I want a per-session transcript check that can flag or correct the source transcript before translation, so that I can measure whether an LLM sanity pass reduces effective error rate.

4.1Cascade modes: off / flag / correct. 4.2Realtime modes: off / flag only; correct not selectable. 4.3Flag is non-blocking. Suspicious segment annotated in the UI; translation proceeds with original text without waiting. 4.4Correct rewrites before translation. Rewritten text goes to translation; displayed source updated; a dedicated latency stage records the check's cost. 4.5Raw vs corrected WER per item in the report. 4.6Off means no call and no extra latency stage. 4.7Check failure is safe. Original transcript used, session continues, non-fatal toast.

Story 5 — Server/offline denoise + curated model pickers Tiers 5–6

As the researcher, I want the server-side and offline-only denoisers plus curated model/voice pickers in the same panel, so that the panel is the complete inventory of processing steps and I can sweep models the same way I sweep denoisers.

5.1[T5] Server denoise selection. off / DeepFilterNet (attenuation limit dB, post-filter strength) / noisereduce (prop_decrease, stationary/non-stationary), each with its parameters visible. 5.2[T5] Applied on the server path — every mic frame processed before Deepgram. 5.3[T5] Capability discovery. Without backend[denoise]: torch stages disabled with "not installed" hint; with it: enabled. Core CI torch-free. 5.4[T5] Offline-only stages visible but disabled ("benchmark only"), selectable in a benchmark config file. 5.5[T5] Wave-U-Net absent if no maintained package — no placeholder, no new decision. 5.6[T6] Model pickers are allow-lists — Realtime model, segmentation model, Deepgram model, translation model, voices; no free text. 5.7[T6] Server-side validation. Out-of-list id → HTTP 400 on the Realtime route; Cascade WS falls back to default (asymmetric posture).

Edge cases the brief must decide

Apply during Cascade TTS playback — a Deepgram reconnect must not strand withheld frames.
Apply during a Realtime reply — session.update mid-response; defer to next turn?
Apply while disconnected — queue for next connect vs disabled.
Rapid repeated Apply — no overlapping Deepgram reconnects.
Reconnect fails after a param change — revert vs surface error.
Extra installed but weights missing — different hint than "not installed".
Retired model id in a stored/imported config.
Malformed JSON import / unknown keys from a newer build.
Corpus WAV missing or wrong format — per-item skip + ffmpeg hint.
Real-recording manifest present but files missing.
Sweep size — N×M browser launches; cap or resume.
Fingerprint collisions / schema-version drift.
"Max denoise" stacking may cancel out or add latency.
Gate threshold at 0 dBFS / −∞ must not crash the worklet.
RNNoise 16k→48k→16k round-trip may itself degrade WER.
Playwright on 5183 vs cors_origins 5173 — WS origin guard.

Out of scope

  • Server-side / account preset storage; GPU paths; Demucs / DNS / Wave-U-Net in the live path; correct in Realtime; mic calibration wizard; new language pairs; supplying the real recording set; auto-generating COMPARISON.md prose; multi-user / auth.

Assumptions (flag if wrong)

  1. Wire key names are a build detail (camelCase on the wire, snake_case in Python).
  2. Fingerprint = short hash (e.g. first 8 hex of SHA-256 over canonical JSON); algorithm is a build detail as long as identical everywhere.
  3. "Live apply" is an explicit Apply action, not auto-apply per keystroke.
  4. Panel is a new component under frontend/src/pages/, backed by a pure tuningConfig.ts module + tests; harness-driven controls carry data-testid.
  5. The uncommitted _turn_detection() / realtime_vad_* work is absorbed; .env stays as server defaults.
  6. Generated noisy audio git-ignored; script + SCRIPT.md committed.

Open questions (with recommendations)

Q1 · Connection-level Cascade change → deliberate Deepgram reconnect: warn first, or do it silently?

Recommendation: no confirmation dialog — Apply reconnects immediately, and the connection badge briefly shows "reconnecting STT" (reusing the existing reconnecting status) so the cost is visible without blocking the lab loop.

Q2 · Does the WER_THRESHOLD = 0.20 pass/fail gate apply to noisy variants?

Recommendation: no — noisy runs are report-only (numbers, no assertion); the 0.20 gate keeps applying to the clean corpus only, so a denoise experiment can never turn CI red.

Q3 · In flag mode, how is a suspicious segment marked?

Recommendation: a small badge on the segment (next to the existing trigger annotation), no toast — toasts are reserved for errors today and a flag per segment would be noisy.
