Placement decision

Chosen

Right-hand collapsible side panel

Toggled by a Tuning button in navbar-end, next to the connection badge. Open, it takes a fixed 400 px column and the transcript grid collapses from sm:grid-cols-2 to a single column — transcripts stay on screen the whole time you tune, which is the entire point of a lab: turn a knob, press Apply, watch the very next segment.

Rejected

Collapsible section under the navbar

Six accordion sections stacked full-width push the transcript cards below the fold. You'd scroll away from the thing you're measuring every time you change a knob. Only wins on implementation cost.

Rejected

Modal dialog

A modal hides the transcripts and the latency strip completely, and the app already reserves the modal treatment for the one blocking case (apply-failed dialog, mock 4c). Two modals with different urgency reads badly.

1 · Collapsed — the panel is shut, the navbar carries the state

Default. The only new pixels on the page are the Tuning button, its monospace fingerprint chip, the amber pending-count badge, and the fingerprint chip that now rides on the end of the latency strip. Fingerprint chip and pending badge are the whole collapsed-state contract: which config am I running, and is what I see on screen actually what's applied?

Three layers, cheapest first:

  • A 1.5 px amber left rule on the row — scannable at a glance while scrolling six sections.
  • An amber dot before the control — survives the left rule being clipped inside a nested card.
  • A was: … badge with the previous applied value — the actual answer to "what did I change?" without opening a diff view.

Rows whose knob is Deepgram-connection-level additionally carry a reconnects chip, which is what flips the Apply label to Apply (reconnects STT).

Open UX questions

1 · Does the panel stay open across a mode switch, and what happens to unapplied changes in the mode you left?

Switching tabs already tears down the live session. The draft config is mode-scoped, so Cascade's pending edits are still sitting there when you come back.

Recommendation Panel stays open; each mode keeps its own draft; pending changes survive the switch untouched and the pending badge reflects the current mode only. No prompt, no discard — losing a carefully-typed set of five VAD numbers because you glanced at the other tab would be the worst thing this panel could do.

2 · Should Apply be blocked while TTS playback is active (Cascade) or a Realtime reply is streaming?

Cascade withholds mic frames during playback; Realtime disables the mic track mid-response. An Apply landing in that window either strands queued audio or gets ignored by the model.

Recommendation Don't block the button — queue it. Apply is accepted immediately, the status line reads "Applying after the current reply…", and the actual session.update / reconnect fires at the next turn boundary. Blocking a button for reasons the user can't see is worse than a one-turn delay they're told about. Same mechanism debounces rapid repeated Applies.

3 · How much of the config does the collapsed navbar chip need to communicate?

"cfg:7f3a9c21" is precise and comparable to a report row, but it says nothing about what is actually on. A named-preset chip ("Max denoise") reads instantly but goes stale the moment you nudge one slider.

Recommendation Show the fingerprint, and put the preset name in the panel header only, with "Preset modified" beside it once the draft diverges. The fingerprint is the join key to every benchmark row — that is the thing you need to read off the screen and paste into COMPARISON.md. Optionally add a native title tooltip on the chip listing the enabled stages.
