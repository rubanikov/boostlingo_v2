Test Dataset & Translation-Quality Testing

Ticket 11 already decided how to test STT accuracy (WER). This ticket decides what the shared test dataset actually contains, and how — or whether — to test translation quality, which WER doesn't touch at all.

The gap WER leaves open: WER only measures whether Deepgram transcribed the right words in the source language. It says nothing about whether the translation stage produced a correct, fluent target-language sentence. The brief names "interpretation quality (subjective + WER)" as a Key Impact Metric — WER is one half of that; nothing in the map yet covers the "subjective" half in a repeatable way.

What WER actually is explaining, per your question

Word Error Rate = (Substitutions + Deletions + Insertions) ÷ (words in the correct reference text) — a Substitution is a word Deepgram heard as the wrong word, a Deletion is a word it missed entirely, an Insertion is a word it hallucinated that was never spoken. Computed by aligning Deepgram's output against the known-correct source text with an edit-distance algorithm (jiwer does this). 0% = perfect transcription; lower is better.

Does the recommended dataset (question 1) cover it? Yes — WER needs exactly what "varied everyday conversation" already is: known source-language sentences, TTS-generated into audio, fed through Deepgram, scored against that known text. It's the same dataset serving double duty: WER checks Deepgram's output against the source text; this ticket's new translation-quality check runs on what comes out the other end of the pipeline, from that same source text. One dataset, two measurement points.

Current state — from ticket 11

TTS-generate ~10–15 known sentences per language (EN, ES), run through STT, score against known source text via edit-distance (jiwer). Plus a Playwright fake-mic E2E test and a noise-rejection case. Fully automated, per decision.

What should the shared dataset actually contain?

Minimal — a few clean sentences

Simple, grammatically tidy sentences. Fastest to build, but doesn't stress-test how the pipeline handles natural speech — filler words, contractions, casual phrasing, mid-sentence corrections.

Varied everyday conversation recommended

~15-20 short items: greetings, questions, requests, casual asides, a couple of contractions/filler words ("um," "you know") — general street conversation, no assumed professional domain. Updated per feedback: also folds in 2-3 longer, multi-clause sentences into the same set (not a separate dataset) — e.g. a run-on sentence with a mid-thought correction — so segmentation gets stress-tested for free within the one varied corpus, instead of needing a dedicated long-sentences-only set.

Long/complex sentences only

Multi-clause sentences throughout, as the entire set. Now redundant with the recommended option above, which already includes a few — kept here only if you want a dedicated stress set instead of folding it in.

Also recommending: include 2-3 longer multi-turn conversation snippets (not just single sentences) — general street conversation like making weekend plans, asking for directions, or a casual complaint about a delayed order. These exercise the segmentation-boundary logic from ticket 05 (does the LLM-hybrid cut clauses sensibly across a real back-and-forth?) and double as ready-made material for the 5-minute stability test (ticket 13), instead of building separate content for each.
question 2 of 3

How do we test translation quality?

The brief says "subjective + WER" — not BLEU/COMET or other automated MT metrics. That's a real signal about scope, not just an omission.

Manual review only

You read/listen to outputs and judge quality by hand for the write-up. Zero build cost, but not repeatable — can't catch a regression between two runs automatically.

+ LLM-as-judge recommended

Manual review stays primary, plus a cheap automated supplement: feed source + translated text to a capable LLM, ask it to rate accuracy/fluency 1-5 and flag mistranslations. One extra API call per test item — matches the brief's "subjective" framing since it's a judgment call, just an automatable one.

Full MT metrics (BLEU/COMET)

Standard MT-research rigor — reference translations, automated scoring pipeline. Real build cost for a metric the brief never asked for; over-engineering relative to "subjective."

What BLEU and COMET actually are explaining, per your question

BLEU (2002, the classic one)

You first need a human-written "reference" translation for every source sentence — the "correct answer." BLEU then counts how many overlapping word-sequences (1-word, 2-word, 3-word, 4-word chunks) the machine's translation shares with that reference, with a penalty if the machine translation is suspiciously short. Output is a 0-100 score — higher means more word-for-word overlap with the reference.

Weakness: purely mechanical word-matching. A perfectly good translation that just phrases things differently than the reference gets punished for "not matching," even though a human would call it correct.

COMET (2020, the modern one)

A small neural model, pre-trained on thousands of real human quality ratings, that reads the source sentence, the machine translation, and (usually) a reference, then predicts the score a human rater would likely give. Because it understands meaning rather than just matching words, it correctly rewards valid paraphrases BLEU would wrongly penalize.

Weakness: still generally needs that same human-written reference translation per sentence — the model just scores against it more intelligently.

The real cost either way isn't running the metric — it's writing a correct human reference translation for every single test sentence first, which is exactly the extra work the "manual + LLM-as-judge" option above avoids, since an LLM judge can rate a translation directly without needing a pre-written reference to compare against.

Which one actually helps improve quality, not just measure it? per your question — LLM-as-judge, and by a clear margin. Prompt it to explain what's wrong, not just output a score ("lost the conditional tense," "translation is too formal for a casual complaint," "dropped the negation entirely") — that's directly actionable in a way a BLEU/COMET number never is; those just tell you quality moved, not why. Manual review gives the deepest nuance but doesn't scale — you can't run it after every prompt tweak. BLEU/COMET are built for tracking aggregate trends across hundreds or thousands of examples in a research pipeline; on a ~15-20 item dataset there isn't enough volume for the number to be statistically meaningful anyway. LLM-as-judge is the one that's both repeatable and gives you something to act on.
