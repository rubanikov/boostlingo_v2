Error Handling & Test Strategy

Two decisions: concrete behavior for each brief-mandated failure mode, and what "critical path" means for the targeted tests the brief requires. The throughline for both: failures are scoped to one segment, never the whole session, with a circuit breaker as the backstop.

question 1 of 2

Error-handling behavior, per failure mode

Failure modeBehaviorUser sees
Rate limit 2 retries, backoff 200ms → 400ms (bounded — real-time voice can't tolerate long waits). Exhausted → drop this segment, keep session alive. Brief non-blocking toast: "Provider busy, retrying…" — only if it takes long enough to notice.
Timeout Per-stage timeout budget tied to ticket 08's latency targets — if a stage overruns its budget, 1 retry, then drop the segment. Segment silently skipped; next utterance proceeds normally.
Empty STT result Usually not an error at all — TranscriptSegment.is_empty (ticket 06) is the correct outcome for silence/noise. Only flagged if SpeechStarted fired but STT still produced nothing — logged, segment dropped, no retry (nothing to retry against). Nothing — silence should look like silence.
Empty translation result A real anomaly (translation shouldn't legitimately return blank for non-empty input) — 1 retry, then logged, segment dropped rather than show untranslated source text (more confusing than a brief gap). Segment silently skipped (logged server-side for debugging).
Mic permission denied Not a provider error — a browser-level NotAllowedError (ticket 07), blocks session start entirely. No auto-retry (requires the user to change browser settings). Blocking error banner (ticket 09) with a "try again" button that re-attempts getUserMedia() once fixed — not a full page reload.
Fallback provider — explicitly not automatic. Ticket 06's swappable-provider design is a build-time/config-time property (the whole point of the abstraction), not a runtime automatic-failover feature. Wiring up live automatic failover between multiple concurrently-connected providers is meaningfully more engineering than a 15-20hr build serves, for a benefit outside what the brief evaluates (one working implementation with swappable providers, not a redundancy system). Stating this explicitly to avoid ambiguity, not leaving it silently unaddressed.
Session termination — circuit breaker, not per-failure. Every failure above is scoped to one segment; the session itself stays alive. The one exception: 5 consecutive segment failures trips a circuit breaker — that pattern suggests something structurally broken (bad API key, provider fully down), not a transient blip, and surfaces a hard "interpretation unavailable" state rather than silently limping along forever. An actual dropped WebSocket connection is a different case, owned by Stability: reconnection, drift, memory (ticket 13), not this ticket.

What counts as "critical path" for tests?

In scope

  • Provider boundary contract tests — each Protocol implementation (ticket 06) tested against a mocked SDK, verifying normal streaming maps correctly to TranscriptSegment/TranslationChunk/AudioChunk, and each failure mode above maps to the right ProviderError kind + retryable flag.
  • Segmentation logic tests — the LLM-hybrid clause-check vs. Deepgram-fallback race (ticket 05) is the single most complex custom logic in the system: fallback fires when the LLM doesn't respond in time, LLM verdict wins when it arrives first, "carry forward" behaves correctly when new words land after a snapshot.
  • Retry/circuit-breaker logic tests — given a provider that fails N times then succeeds, correct attempt count and backoff timing; given 5 consecutive failures, the circuit breaker actually trips.
  • End-to-end pipeline — already decided (ticket 11): the Playwright fake-mic E2E test exercises the whole real pipeline, not just isolated units. This ticket's tests complement it rather than duplicating it.

Explicitly not in scope

Matches the brief's own "full coverage not required": exhaustive testing of every provider's every documented parameter, UI component snapshot tests, load/stress testing, multi-provider combinatorial testing (only one provider per category is actually implemented — ticket 06's scope).

Tooling: pytest + pytest-asyncio for the async provider/segmentation logic, with hand-mocked provider SDKs or fake WebSocket connection objects rather than live network calls — fast, deterministic, no flakiness from real API dependencies in the test suite.

Real recordings alongside the TTS-generated corpus good addition, per your feedback

Genuinely valuable and worth doing: TTS-generated audio (ticket 11/14's corpus) is clean and consistent — it validates the pipeline mechanically but can't surface how the system handles real background noise, natural volume/distance variance, or actual voice characteristics the way a real recording does. It's also the only real way to validate that the autoGainControl/noiseSuppression/echoCancellation constraints (ticket 07) are actually doing something, rather than just assuming they are.

No new test infrastructure needed — this drops directly into the harness ticket 11 already decided: the Playwright fake-mic E2E test feeds a WAV file via Chrome's --use-file-for-fake-audio-capture flag, and that flag doesn't care whether the file is TTS-generated or a real recording. Real recordings become additional fixture files run through the exact same WER/E2E harness, not a parallel system.

Practically: record a handful of real clips (varied conditions — quiet room, some background noise, normal speaking distance vs. a bit farther from the mic) covering the same ticket 14 sentence set or a subset of it, and drop them in alongside the TTS fixtures. Worth treating these as supplementary/manual-tier rather than blocking automated CI on a real voice recording being available — same spirit as ticket 11's "device coverage is a manual pass, not automated" call.
