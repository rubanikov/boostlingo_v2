question 1 of 2

Capture: MediaRecorder or AudioWorklet?

This isn't actually one answer for the whole app — the two modes need genuinely different mechanisms after the shared getUserMedia() call.

Realtime mode — neither

WebRTC (ticket 03) handles capture, encoding, and transport natively once you call pc.addTrack(stream.getTracks()[0]) on the raw MediaStream. No worklet, no recorder — the browser's WebRTC engine does the rest.

Cascade mode — AudioWorklet recommended

Deepgram wants raw PCM binary frames, no container (ticket 04's research). AudioWorklet gives direct access to raw samples on the audio thread; convert Float32→Int16, buffer to ~20-40ms per WebSocket frame (its native 128-frame callback size is too chatty to send per-callback). MediaRecorder would hand back compressed webm/opus blobs at coarse timeslices — wrong shape entirely, and would force Deepgram to decode a container server-side for no benefit.

The level meter + VAD-state UI (ticket 11) taps an AnalyserNode off the same raw MediaStream regardless of mode — genuinely shared, mode-agnostic code, satisfying the "clean separation between mode-specific transport and mode-agnostic UI" bar directly rather than just asserting it.

Why Float32 → Int16, and what about rounding? answering your question

Why the conversion: Web Audio API's AudioWorklet always hands you samples as 32-bit IEEE float in the range -1.0 to 1.0 — that's just the browser's internal format, not a choice. 16-bit signed integer PCM ("linear16") is the de facto standard raw format for streaming ASR APIs generally, Deepgram included (ticket 04's research). It's not strictly the only option — Deepgram's docs also list a "linear32" mode — but that almost certainly means 32-bit integer PCM, a different byte layout than Web Audio's IEEE float, not a way to skip conversion entirely. Flagging honestly: which exact encodings Deepgram accepts wasn't re-verified here, this is carried over from ticket 04. Int16 is the pragmatic default: half the bytes of int32 over the wire, and its ~96dB dynamic range is already far more than speech or consumer mic hardware need.

Rounding: it's a plain linear scale-and-clamp, nothing fancier — int16 = clamp(round(float32 * 32767), -32768, 32767). No pre/post-processing like dithering is applied, and that's a deliberate omission, not an oversight: dithering (adding tiny controlled noise before quantizing) is a professional audio-mastering technique for when human ears are critically listening to the result. Here the destination is an ASR model, not a listener — 16-bit quantization noise sits far below the noise floor of any consumer microphone and below the dynamic range speech actually uses, so it's inaudible/immaterial in practice, and STT models are trained on oceans of naturally 16-bit audio already. The actual quality-limiting factors in this pipeline are mic hardware and network conditions, not this rounding step.

question 2 of 2

Playback: how do incrementally-arriving audio chunks get played?

Streamed <audio> src

Simplest API, but a poor fit for true chunk-by-chunk streaming — wants a complete-ish resource, not a running feed of separately-arriving fragments.

MediaSource Extensions

SourceBuffer.appendBuffer() works for compressed, container-aligned chunks — but adds real complexity (codec/container fragment alignment) and is designed more for adaptive video streaming than lowest-latency voice.

Web Audio API scheduling recommended (Cascade)

Request raw PCM from ElevenLabs (skips decoding entirely). Each chunk becomes an AudioBuffer, scheduled via AudioBufferSourceNode.start(nextTime) where nextTime tracks the previous chunk's end — gapless, sample-accurate, and you can start playing the very first chunk the instant it arrives.

Realtime mode doesn't need any of this. WebRTC delivers the model's audio as a media track via pc.ontrack — assign e.streams[0] straight to an <audio> element's srcObject (the exact pattern in OpenAI's own openai-realtime-console, ticket 02's research). The browser's native jitter buffer and audio pipeline handle playback — manual scheduling is a Cascade-mode-only concern.

MSE vs. Web Audio API, in full answering your question

MediaSource Extensions

  • Pro: purpose-built browser API for streaming into <audio>/<video>; handles buffering/underrun via the browser's own media pipeline.
  • Pro: works well with compressed formats — smaller bandwidth if streaming Opus/MP3.
  • Con: chunks must be valid, container-aligned codec fragments — ElevenLabs' streamed output doesn't naturally arrive pre-chunked at clean fragment boundaries, so this is real added complexity, not a drop-in fit.
  • Con: designed around adaptive video streaming's latency budget, not lowest-latency voice — wants a sourceopen + initial segment before playback starts, adding startup latency vs. scheduling audio the instant it arrives.
  • Con: no natural way to tie playback position back to segmentId for UI sync (e.g. highlighting the currently-speaking segment in the transcript, ticket 09) — that's opaque inside the browser's buffer.

Web Audio API scheduling

  • Pro: works directly with raw PCM — no decode step, pairs naturally with requesting raw PCM from ElevenLabs.
  • Pro: minimal startup latency — first chunk plays the instant it's turned into an AudioBuffer, no waiting on MSE's readiness machinery.
  • Pro: full control over scheduling means each AudioBufferSourceNode can carry its segmentId — enables exact "now playing this segment" UI sync for free.
  • Con: you own the bookkeeping — the "next scheduled time" pointer, and handling gaps if network is slow, rather than getting that from browser-managed buffering.

Net: MSE's strengths (compressed formats, browser-managed buffering) don't line up with what this app actually needs (raw PCM, segment-aware UI, lowest possible startup latency) — recommendation stands.

Will the target text look smooth or stuttery? answering your question

Within one segment: smooth, like any LLM chat UI's streaming text — tokens arrive with small, irregular gaps (typically tens of milliseconds), but human reading speed is far slower than that, so it reads as natural incremental typing, not stutter. That's the same pattern essentially every LLM chat product uses. Implementation caveat worth stating plainly, not just assuming: this only holds if the UI appends new text rather than re-rendering the whole block on every token — a full re-render per token is a common mistake that does cause visible jank, independent of how smooth the underlying token stream is.

Between segments: a real, natural-feeling pause — while the next chunk of speech is captured, transcribed, and judged complete (ticket 05's segmentation), no target text is arriving at all. This isn't a flaw to hide; it mirrors the actual pause in the spoken audio, so the text experience and the audio experience stay in sync with each other rather than one looking "laggy" relative to the other.

Browser gotchas worth pinning down now

  • Autoplay policy: browsers block audio playback without a prior user gesture. Since starting a session already requires a click (to trigger the mic-permission prompt), reuse that same gesture to create/resume() the AudioContext — don't create it lazily on first audio arrival, or playback can silently fail.
  • Mic permission denied: getUserMedia() rejects with a NotAllowedError specifically — catch that named error for the brief's mic-permission-denied error case (ticket 10) rather than a generic catch-all.
  • getUserMedia constraints (ticket 11, already decided): autoGainControl, noiseSuppression, echoCancellation all set to true at the one shared capture call, before the mode split.
