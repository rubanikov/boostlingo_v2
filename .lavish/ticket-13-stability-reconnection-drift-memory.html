Stability: Reconnection, Drift, Memory

The last decision on the map. Three sub-questions, and two of them turn out to already be answered by earlier decisions — this ticket mostly wires those together rather than inventing new mechanisms.

question 1 of 3

Reconnection — what happens when a connection drops mid-session?

Backend ↔ Provider (Deepgram/ElevenLabs)

Backend detects the drop, attempts reconnect with backoff (500ms → 1s → 2s, capped), without tearing down the browser↔backend WebSocket — transparent where possible. Any segment in flight when the drop happens is dropped and logged (ticket 10's "scoped to one segment" philosophy extended here, not a new rule). If reconnect attempts are exhausted, this reuses ticket 10's circuit breaker — the same "something structurally broken" signal, not a parallel concept.

Browser ↔ Backend

The more realistic real-world failure (wifi handoff, laptop sleep) — browser attempts a short-window reconnect (a few seconds, backend keeps session state alive that long). Scoping call: full session-resumption beyond that short grace window is out of scope for the time budget — if it fails, the session ends and the user restarts manually. Named explicitly rather than silently left undefined.

User sees a visible "Reconnecting…" state — the connection-status badge in ticket 09's winning layout (currently "Connected") is the natural home for this: turns yellow/amber during a reconnect attempt, without disrupting the rest of the screen. Subtle, not alarming — same pattern as Slack/Zoom's reconnect indicators.

question 2 of 3

Audio / clock drift

Clock drift (for latency display) — already answered by ticket 08. Offset re-computed every 30s, plus after any reconnect. This ticket's reconnection design (question 1) is exactly one of the resync triggers ticket 08 already specified — no new mechanism, just confirming the wiring: a reconnect event fires the same offset-resync ticket 08 defined.
Audio playback drift — not actually a risk, thanks to segmentation already being decided. Web Audio API buffer-scheduling drift (accumulated floating-point error across many scheduled buffers) would only matter for one continuous unbroken playback stream lasting the whole 5 minutes. But ticket 05's segmented architecture means playback happens in short per-segment bursts with natural gaps between them — each segment's AudioBufferSourceNode chain (ticket 07) starts scheduling fresh from "now," not building on a stale multi-minute-old pointer. No accumulation within a segment (a few seconds, imperceptible) and none across segments (each starts clean). A genuine side-benefit of the segmentation decision, not something requiring new design work here.
Realtime mode: WebRTC's own jitter buffer and audio pipeline is engineered specifically for long-running continuous real-time audio without drift — that's core to what WebRTC does. Nothing for this project to add.
question 3 of 3

Memory bounds

What could growVerdictWhy / mitigation
Transcript text history negligible A 5-minute conversation is maybe 30-60 segments — a few KB of text total. Not worth engineering around at this scale.
Raw audio buffers (in/out) real, but simple ~10MB of raw PCM over 5 minutes if never released. Fix: release each chunk's reference once sent (STT) or played (TTS) — don't push incoming chunks into an ever-growing array "for later."
Per-segment orchestrator state real, but simple Reset cleanly after each segment boundary fires — keep a small rolling window (last 1-2 segments) for display/debugging, not a growing list of every segment since session start.
WebSocket send/receive queues apply backpressure If a queue exceeds a threshold under slow network, that's itself a signal worth logging — not something to let grow silently forever.
Testable addition to ticket 10's suite, not just a design principle: run the Playwright E2E test for a full simulated 5-minute session with a simple process-memory check (e.g. via psutil) before/after, to catch leak regressions empirically rather than relying on code review alone.
