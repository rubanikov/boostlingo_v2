# Research: Browser SPA integration with OpenAI Realtime API (gpt-realtime)

**Question:** How should a browser SPA integrate with OpenAI's Realtime API (model `gpt-realtime`) for voice-to-voice interpretation?

**Method note on sourcing:** OpenAI's docs currently live at `developers.openai.com/api/docs/...` — `platform.openai.com/docs/...` URLs now 301-redirect there, so that is treated as the primary docs domain below. OpenAI's marketing blog (`openai.com/index/...`) returned HTTP 403 to automated fetches in this session for every post tried (`introducing-gpt-realtime`, `advancing-voice-intelligence-with-new-models-in-the-api`), so those specific announcements could not be read directly. Where a claim originates only from that blocked blog, it is marked **[unverified-primary]** below and attributed to the closest first-party channel that echoes it (usually OpenAI's own Developer Community forum, which is first-party but not the platform-docs "spec of record") or to secondary tech coverage, per the research method's instruction to be explicit about provenance.

---

## (a) Direct browser-to-OpenAI WebRTC and ephemeral client secrets

**OpenAI's own recommendation:** for client devices (browser or mobile), use WebRTC, not WebSocket. From the WebRTC guide: *"When connecting to a Realtime model from the client (like a web browser or mobile device), we recommend using WebRTC rather than WebSockets for more consistent performance."* — [Realtime API with WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc). The general conversations guide repeats this for the playback side specifically: *"To play output audio back on a client device like a web browser, we recommend using WebRTC rather than WebSockets. WebRTC will be more robust sending media to client devices over uncertain network conditions."* — [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations).

OpenAI documents **two** browser-connection patterns; only one of them is a true direct browser↔OpenAI connection:

1. **"Unified interface" (signaling relay only).** The browser creates an `RTCPeerConnection`, generates an SDP offer, and **POSTs that SDP to your own server**. Your server attaches session config, forwards it to OpenAI's `POST /v1/realtime/calls` authenticated with a *standard* (non-ephemeral) API key, and returns OpenAI's SDP answer to the browser. After that handshake, the browser's peer connection talks to OpenAI's media/data-channel infrastructure directly — your server is only in the path for the one-time signaling exchange, not for ongoing audio. Source: [Realtime API with WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc).
2. **Ephemeral client-secret approach (fully direct after token mint).** Your server calls `POST /v1/realtime/client_secrets` with a standard API key to mint a short-lived token (value prefixed `ek_`). The browser receives only that token, creates its own `RTCPeerConnection`, and **POSTs its SDP offer directly to OpenAI**, authenticating with the ephemeral token; OpenAI returns the SDP answer directly to the browser. Your server is off the path entirely once the token is issued. Sources: [Realtime API with WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc), [Client Secrets API reference](https://developers.openai.com/api/reference/typescript/resources/realtime/subresources/client_secrets).

**Ephemeral token mechanics:**
- Endpoint: `POST /v1/realtime/client_secrets`. Request takes `expires_after` (expiration policy for the secret) and a `session` object that can **pre-configure** the eventual session — instructions, audio format, voice, turn detection, etc. — so the browser never needs to (and never should) set those from untrusted client code. Response returns `value` (the `ek_...` token), `expires_at`, and the effective `session` object. Source: [Client Secrets API reference](https://developers.openai.com/api/reference/typescript/resources/realtime/subresources/client_secrets).
- Default/range for `expires_after.seconds`: search-engine indexing of OpenAI's reference page (the `platform.openai.com` mirror of this same endpoint 403'd on direct fetch this session) reports a default of 600 seconds (10 minutes) and an allowed range of 10–7200 seconds. **[unverified-primary — could not confirm the literal numbers by direct fetch; only via search snippet of an OpenAI reference page]**.
- Important nuance found consistently across sources: token expiration only gates the window in which the token can be **used to start** a WebRTC/WebSocket session. Once a session has been established with a still-valid token, the session itself is not torn down when the token later expires. Practical implication: mint short-lived, single-use tokens per session-start, not per audio-chunk.
- Data channel: audio/text events flow over a WebRTC data channel literally named `"oai-events"` (`pc.createDataChannel("oai-events")`), carrying the same JSON client/server event schema used on WebSocket. Inbound model audio arrives via the peer connection's `ontrack` handler — *"you don't have to handle audio events from the model in the same granular way you must with WebSockets."* Source: [Realtime API with WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc).
- Security: using a standard (long-lived) API key directly in the browser is explicitly called out as unsafe — ephemeral tokens exist specifically to avoid that. An `OpenAI-Safety-Identifier` header (a hashed/stable per-user ID) should be set server-side, either on the unified-interface relay call or at token-mint time; when set at mint time, *"the browser does not need to send the safety identifier when it later connects with that token."* Source: [Realtime API with WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc).

**Bottom line for (a):** Yes — OpenAI explicitly supports and recommends a genuinely direct browser↔OpenAI WebRTC media path, gated only by a backend-minted, short-lived ephemeral token; the backend is not in the audio path at all once the token is issued (only in the "unified interface" variant does the backend stay in the path, and even then only for the one-time SDP handshake, not for ongoing media).

## (b) WebSocket relay alternative (browser → backend → OpenAI) and its latency cost vs (a)

OpenAI's WebSocket transport is documented as a **server-to-server** transport, not a client transport:
- Connection: backend connects to `wss://api.openai.com/v1/realtime?model=...` using a standard API key in an `Authorization: Bearer` header. Source: [Realtime API with WebSocket](https://developers.openai.com/api/docs/guides/realtime-websocket).
- OpenAI's explicit guidance: *"if you are connecting from a client like a browser or mobile app, WebRTC will be a more robust solution in most cases."* — same page. The guide gives no browser-direct WebSocket examples, only Node.js/Python backend and one browser illustration that itself still requires an ephemeral token (it does not present browser-WS as the recommended path).

**Why a browser can't safely go straight to OpenAI over WebSocket the way it can over WebRTC-with-ephemeral-token:** the docs describe WebSocket auth as the standard API key pattern ("your backend system will connect via WebSocket directly to the Realtime API"); nothing in the WebSocket guide describes an ephemeral-token-authenticated *browser*-to-OpenAI WebSocket flow the way the WebRTC guide does. Practically, a browser that wants OpenAI's WebSocket endpoint must go through a backend relay for the **entire session**, not just the handshake — because the credential that authenticates the WebSocket (a standard API key) cannot be handed to the browser at all.

**This is the structural latency difference from (a):**
- In the WebRTC ephemeral-token path, the backend is only ever involved in issuing a token (one short HTTP round trip, before the call even starts); every subsequent audio frame flows browser ⇄ OpenAI media servers directly over a UDP-based, jitter-buffered, congestion-adaptive transport designed for real-time media.
- In a WebSocket relay, every audio frame must traverse **two** hops for the life of the call: browser → your backend → OpenAI, and OpenAI → your backend → browser. Each hop adds its own network RTT, base64 encode/decode and JSON-framing overhead (WebSocket audio is sent as base64-encoded PCM16 chunks per the guide's code samples — the OpenAI cookbook example notes *"sending audio with WebSockets requires work to manage the inbound and outbound PCM16 audio streams"*, [One-Way Translation cookbook](https://github.com/openai/openai-cookbook/blob/main/examples/voice_solutions/one_way_translation_using_realtime_api.mdx)), and TCP head-of-line blocking under any packet loss (WebSocket rides on TCP; WebRTC media rides on UDP/SRTP specifically to avoid this).
- **OpenAI's docs do not publish a quantified number for "how much slower" a relay is** — the only documented claim is qualitative: WebRTC gives "more consistent performance" / is "more robust... over uncertain network conditions" than WebSocket for client media. No millisecond delta between the two transports is stated in the docs reviewed. Treat the above hop-count/protocol reasoning as inference grounded in the documented facts, not a vendor-supplied number.

**When a relay is still relevant to this project:** the ticket's *cascade* mode (STT → Translation → TTS) inherently needs a backend in the loop to call separate STT/MT/TTS providers, so a WebSocket-style backend-mediated pipeline is architecturally required there regardless of what's chosen for the Realtime voice-to-voice mode. The (a) vs (b) choice is specifically about the *Realtime API* voice-to-voice mode's transport, not about whether the app has a backend at all.

## (c) What gpt-realtime requires/supports for translation specifically

This is where the model landscape matters a lot, and it forks the answer:

### The model family, precisely
- `gpt-realtime` (the model named in the ticket) is a **general voice-agent** model. Model card: 32,000-token context window, 4,096 max output tokens, default snapshot `gpt-realtime-2025-08-28`, knowledge cutoff Oct 1 2023, supports **only** the `v1/realtime` endpoint (no chat completions, no translation, no transcription endpoints). Source: [GPT-Realtime model card](https://developers.openai.com/api/docs/models/gpt-realtime).
- On **May 7, 2026** OpenAI additionally released three companion models together, per the changelog: `gpt-realtime-2` (adds configurable reasoning effort to speech-to-speech, 128K context), `gpt-realtime-translate` (dedicated streaming speech-to-speech **translation** model), and `gpt-realtime-whisper` (dedicated streaming speech-to-text). Source: [OpenAI API changelog](https://developers.openai.com/api/docs/changelog); corroborated by the model card [GPT-Realtime-2 model card](https://developers.openai.com/api/docs/models/gpt-realtime-2) and secondary coverage of the announcement date.
- On **July 6, 2026**, OpenAI released `gpt-realtime-2.1` and `gpt-realtime-2.1-mini`, updating the reasoning line with better alphanumeric recognition, noise/silence handling, and interruption behavior, plus a documented latency improvement (see section (d)). Source: [OpenAI API changelog](https://developers.openai.com/api/docs/changelog), [GPT-Realtime-2.1 model card](https://developers.openai.com/api/docs/models/gpt-realtime-2.1).
- **These are separate model names, not an alias that transparently upgrades** — `gpt-realtime`'s documented default snapshot is still the original August 2025 one; `gpt-realtime-2` / `gpt-realtime-2.1` / `gpt-realtime-translate` are distinct models you must explicitly request. This is directly relevant to a project whose ticket names `gpt-realtime` specifically.

### Path 1 — steering plain `gpt-realtime` to translate instead of converse
`gpt-realtime` has no dedicated "translation mode" flag. The only documented lever is the **`instructions` field** (system prompt), which the conversations guide describes as shaping model behavior generally (*"You can still set direct session fields; these override prompt fields if they overlap,"* example instruction: *"Speak clearly and briefly. Confirm understanding before taking actions"*) — source: [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations). OpenAI's own cookbook demonstrates exactly this steering pattern for translation (on the older `gpt-4o-realtime-preview-2024-12-17`, but the mechanism is the same field): it avoids conversational replies by writing explicit, few-shot-laden instructions per language pair (e.g. *"we want a direct translation of that question"*, with language-specific prompt files for French/Spanish/Tagalog/English/Mandarin). Source: [Multi-Language One-Way Translation cookbook](https://github.com/openai/openai-cookbook/blob/main/examples/voice_solutions/one_way_translation_using_realtime_api.mdx).
- **No structured language-pair parameter exists for `gpt-realtime` sessions.** Language is expressed purely in natural-language instructions text; nothing in the model card or session-config guides documents a `source_language`/`target_language` field for the general realtime endpoint.
- **Turn-based limitation for interpretation:** the cookbook is explicit that this steering approach inherits the model's turn-based conversational design: *"The speaker must pause briefly to allow the model to process and translate speech"* — continuous/overlapping simultaneous interpretation is not how a `response.create`-driven conversation session behaves; it responds after a turn is detected as complete (see VAD/turn_detection below), then speaks. The cookbook's own framing is that this is a workaround on a conversational model, not a purpose-built translation flow, and that OpenAI expected it to improve as models got faster — which is exactly what the `gpt-realtime-translate` release (Path 2) is.
- **Audio format for `gpt-realtime` sessions:** session-level `audio.input.format` / `audio.output.format` fields take a typed object, e.g. `{"type": "audio/pcm", "rate": 24000}` for PCM16, or `{"type": "audio/pcmu"}` / `{"type": "audio/pcma"}` for G.711 μ-law/A-law. Source: [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations) (direct primary confirmation of the `audio/pcm` and `audio/pcmu` type strings); the third option (`audio/pcma`) and the umbrella union-type name (`RealtimeAudioFormats`) were corroborated via the API reference page indexed by search but not independently re-fetched in full this session — flagged as **[secondary-confirmed]**.
- **Turn detection / VAD:** enabled by default; documented options include `server_vad` and `semantic_vad` types, or `turn_detection: null` to disable entirely (push-to-talk). You can also keep VAD active for speech-boundary detection while suppressing automatic responses via `interrupt_response: false` / `create_response: false`, then trigger `response.create` yourself. Source: [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations). Exact default numeric thresholds (e.g. silence-duration-ms) were not confirmed against GA reference docs in this session — flag for verification against the SDK type definitions at implementation time.
- **Interim transcripts for live captions (general session):** two separate delta streams exist —
  - User/source speech: `conversation.item.input_audio_transcription.delta` (requires configuring input transcription on the session) — source: [Realtime server events reference](https://developers.openai.com/api/reference/resources/realtime/server-events) (via search-indexed content; not independently re-fetched in full — **[secondary-confirmed]**).
  - Model/output speech: `response.output_audio_transcript.delta` (streaming) and `response.output_audio_transcript.done` (final) — source: [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations), directly fetched. Note the field name uses the GA-era `output_audio_transcript` naming (the guide separately mentions the GA migration moved "output audio configuration under `session.audio.output`" — [Realtime and audio overview](https://developers.openai.com/api/docs/guides/realtime)); older beta-era docs/blog posts referred to `response.audio_transcript.delta` without the `output_` infix, so **verify the exact event name against the current SDK types at implementation time** rather than trusting any single source here, since the API went through a beta→GA rename.
- **Voice options:** `alloy, ash, ballad, coral, echo, sage, shimmer, verse, marin, cedar`, with `marin`/`cedar` recommended for best quality; voice cannot be changed mid-session once audio has been produced. Source: [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations).

### Path 2 — the purpose-built `gpt-realtime-translate` model (relevant even though the ticket names `gpt-realtime`)
This is a materially different, and directly on-topic, finding: OpenAI ships a **dedicated translation session type** that is architecturally distinct from a `gpt-realtime` conversation session:
- Dedicated endpoints: `POST /v1/realtime/translations/client_secrets` (ephemeral token mint) and `POST /v1/realtime/translations/calls` (WebRTC SDP) for browser use; `wss://api.openai.com/v1/realtime/translations?model=gpt-realtime-translate` for server WebSocket use. Source: [Realtime translation guide](https://developers.openai.com/api/docs/guides/realtime-translation).
- **Not turn-based / no `response.create`:** the guide states the model streams continuously from incoming audio and explicitly instructs not to call `response.create` and not to wait for a committed user turn before translation begins — *"the model acts as an interpreter"* rather than a conversational assistant. Source: [Realtime and audio overview](https://developers.openai.com/api/docs/guides/realtime); [Realtime translation guide](https://developers.openai.com/api/docs/guides/realtime-translation).
- **Structured language targeting:** target language is set via `audio.output.language` (e.g. `"es"`); source language is auto-detected from incoming audio rather than explicitly configured. This is the structured language-pair field that `gpt-realtime` itself lacks. Source: [Realtime translation guide](https://developers.openai.com/api/docs/guides/realtime-translation).
- **Native interim transcripts for captions on both sides:** `session.input_transcript.delta` (source-language fragments, requires `audio.input.transcription` configured) and `session.output_transcript.delta` (translated fragments) — documented as *"append-only text fragments"* clients should concatenate carefully (*"should not insert unconditional spaces between deltas"*), each optionally carrying `elapsed_ms` for stream sync. Source: [Realtime translation server events reference](https://developers.openai.com/api/reference/resources/realtime/translation-server-events).
- **Audio out:** `session.output_audio.delta` delivers translated audio as base64 PCM16 in ~200 ms frames, default 24kHz mono. Source: [Realtime translation server events reference](https://developers.openai.com/api/reference/resources/realtime/translation-server-events).
- **Language coverage:** secondary coverage (echoing an OpenAI blog post that returned 403 on direct fetch) reports 70+ input languages and 13 output languages (English, Spanish, Portuguese, French, German, Italian, Russian, Chinese, Japanese, Korean, Hindi, Indonesian, Vietnamese). **[unverified-primary — sourced from search-engine synthesis of an OpenAI announcement blog post that could not be fetched directly (403); treat the exact language list as needing re-verification against the live model card before relying on it]**.
- **Model card specifics:** 16,000-token context, 2,000 max output tokens, knowledge cutoff Sep 30 2024, priced per-minute of audio ($0.034/min) rather than per-token, and — notably — **only** supports the `v1/realtime/translations` endpoint, not `v1/realtime`. Source: [GPT-Realtime-Translate model card](https://developers.openai.com/api/docs/models/gpt-realtime-translate).
- **Explicit guidance:** one translation session should be created per target language (i.e., a 2-way interpretation UX needs two concurrent sessions, one per direction) — source: [Realtime translation guide](https://developers.openai.com/api/docs/guides/realtime-translation) (via search-indexed synthesis of the guide; core session-creation/endpoint facts were independently confirmed by direct fetch, this specific one-session-per-target-language framing is **[secondary-confirmed]**).
- **No `instructions` field documented for translation sessions** — the guide's session-config surface centers on `audio.output.language`, transcription toggles, and audio format, not on a system prompt; this is architecturally consistent with the model having a fixed "interpreter" role rather than an open-ended persona to steer.

**Bottom line for (c):** if the goal is literally "translate, don't converse," OpenAI's documentation shows two different documented ways to get there on two different models — prompt-engineer `gpt-realtime` (turn-based, flexible, but requires you to build your own turn-taking/caption-pairing logic and accept the "pause between utterances" limitation the cookbook flags) or use the purpose-built `gpt-realtime-translate` translation session (continuous, structured language targeting, native dual transcript-delta streams, but a separate model/endpoint from the one named in the ticket, with its own pricing and a smaller context window). This fork is worth surfacing to the human even though the ticket names `gpt-realtime` specifically, since it directly bears on how much custom translation-steering work is needed.

## (d) Latency characteristics relevant to a <1.5s end-to-end target

**What OpenAI's platform docs state directly (primary, fetched):**
- The single-model audio-in/audio-out design is framed as inherently lower latency than a chained pipeline: *"This enables lower latency for voice interfaces"* when audio flows directly through one model instead of separate STT/LLM/TTS stages. Source: [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations).
- Reasoning effort trades directly against latency: for `gpt-realtime-2.1`, the model card states *"higher reasoning effort can increase latency and output token usage,"* and the general voice-agents guide recommends starting new production voice agents at `reasoning.effort: low`. Sources: [GPT-Realtime-2.1 model card](https://developers.openai.com/api/docs/models/gpt-realtime-2.1), [Realtime and audio overview](https://developers.openai.com/api/docs/guides/realtime).
- For dedicated transcription sessions (`gpt-realtime-whisper`/streaming transcription), latency is an explicit, developer-controlled dial: *"Lower delay settings produce earlier partial text, while higher delay settings can improve transcript quality"* — i.e., OpenAI documents a latency/accuracy tradeoff knob rather than a fixed number. Source: [Realtime and audio overview](https://developers.openai.com/api/docs/guides/realtime).
- For translation sessions specifically, the guide's own guidance is to **benchmark yourself** — it recommends developers measure "first translated audio latency" and "end-of-utterance latency" for their own deployment, and does not publish a target number. Source: [Realtime translation guide](https://developers.openai.com/api/docs/guides/realtime-translation).
- **No page reviewed in `developers.openai.com/api/docs/...` states a single committed end-to-end latency number** (e.g., no "gpt-realtime responds in Xms" claim was found in the docs proper).

**What OpenAI has said in first-party announcement channels (not platform docs; degraded confidence per the note at the top):**
- OpenAI's own Developer Community forum announcement for the July 6, 2026 release states: *"we've also reduced p95 latency by at least 25% across Realtime voice models through improved caching"* for `gpt-realtime-2.1`/`gpt-realtime-2.1-mini`. Source: [OpenAI Developer Community — New Realtime models: gpt-realtime-2.1](https://community.openai.com/t/new-realtime-models-on-the-api-gpt-realtime-2-1-and-gpt-realtime-2-1-mini/1385896). This is a relative improvement claim (25% off some unstated baseline p95), not an absolute millisecond figure, and it applies to the 2.1 line, not the `gpt-realtime` snapshot named in the ticket.
- The underlying `openai.com/index/introducing-gpt-realtime/` and `openai.com/index/advancing-voice-intelligence-with-new-models-in-the-api/` posts — which appear to be the origin of widely-repeated numbers like "~200ms machine-side latency" and "250–500ms end-to-end" for the realtime model family — returned HTTP 403 to this session's fetch tool and could not be read directly. Every number of that shape found during this research (e.g., sub-200ms round-trip, 250–500ms end-to-end, 300–600ms median time-to-first-audio-chunk) came from third-party tech press (MarkTechPost, DataCamp, various AI-news blogs) paraphrasing those blog posts, not from text this research could independently confirm on an OpenAI-owned page. **Per the research method's instruction not to treat secondary blog posts as source of truth, these specific millisecond figures should be treated as unverified until someone with blog access (or a logged-in browser) re-pulls the original OpenAI announcement text.**

**Practical implication:** OpenAI does not publish, in the docs surfaces this research could access, a single authoritative "speech-end to first-audio-out" number to hold a <1.5s target against. The documented posture is architectural (single-model audio path, reasoning-effort dial, transcription-delay dial) plus "benchmark it yourself" for translation specifically — not a vendor SLA. Any <1.5s target should be validated empirically against this project's own network path and chosen configuration (transport, reasoning effort, VAD settings, model snapshot) rather than assumed from marketing figures.

## Implications for this project

- **Transport for the Realtime voice-to-voice mode:** OpenAI's own guidance and the structural hop-count argument both favor a **direct browser↔OpenAI WebRTC connection using a backend-minted ephemeral client secret** over a full WebSocket relay, specifically because a WebSocket relay keeps every audio frame passing through an extra backend hop for the life of the call — a real cost against a <1.5s budget, even though OpenAI does not quantify it. The backend's only required role in the WebRTC-ephemeral path is minting `POST /v1/realtime/client_secrets` tokens (short-lived, single-use per session-start) — it does not need to touch audio at all for that mode.
- **The cascade mode still needs a backend in the audio path** by construction (separate STT/MT/TTS calls), so this app will run two different transport topologies side by side: direct-to-OpenAI for the Realtime mode, backend-mediated for the cascade mode. That asymmetry is inherent to the two modes, not a choice to avoid.
- **Translation-specific behavior is a real fork, not just a prompting detail.** `gpt-realtime` (named in the ticket) has no native translation mode, no structured language-pair field, and is turn-based (documented limitation: caller must pause between utterances) — getting it to act as an interpreter is a prompt-engineering exercise on top of a conversational model. OpenAI's `gpt-realtime-translate` model, on a separate endpoint, is purpose-built for exactly this: continuous (non-turn-based) translation, structured target-language config, and native dual transcript-delta streams that map directly onto a live-captions UI. Since captions and language-pair handling are both named requirements in this ticket, whoever makes the design decision should explicitly decide whether to steer `gpt-realtime` or adopt `gpt-realtime-translate`/its session type — the two imply different session lifecycles (`response.create`-driven vs continuous) and different caption event names.
- **Live captions:** both paths expose delta-based streaming transcripts usable for captions, but the event names differ by path (`conversation.item.input_audio_transcription.delta` / `response.output_audio_transcript.delta` for a `gpt-realtime` conversation session vs `session.input_transcript.delta` / `session.output_transcript.delta` for a `gpt-realtime-translate` translation session) — and this research flags that the conversation-session event names in particular went through a beta→GA rename, so they should be re-verified against current SDK type definitions before being hard-coded.
- **Latency budget:** no vendor-published absolute number exists to check the <1.5s target against (the widely-cited "~200-500ms" figures trace back to blog posts this research could not access directly and are therefore unverified). Available, documented latency *levers* are: transport choice (WebRTC vs relay), `reasoning.effort` (lower = faster, explicitly recommended default for production voice agents), VAD/turn-detection tuning (silence-duration and semantic-VAD eagerness affect how quickly a "turn" is considered finished and a response begins), and, for transcription, an explicit delay-vs-quality dial. The <1.5s target should be treated as something this project measures against its own build, not something OpenAI's docs guarantee.
- **Audio format compatibility:** both `gpt-realtime` and translation sessions support PCM16 (typically 24kHz) plus G.711 μ-law/A-law at the session-config level — worth knowing if the cascade mode's STT/TTS vendors are chosen to share a common audio format/pipeline with the Realtime mode.
