# Research: Prior art / reference implementations for cascade & realtime voice pipelines

**Scope:** This is a survey of existing open-source code and official reference implementations relevant to building an "AI Interpreter Workbench" — a browser SPA with (1) an OpenAI Realtime API voice-to-voice mode and (2) a separate streaming STT→Translation→TTS cascade mode, provider-swappable, streaming throughout, with per-stage latency instrumentation. It is **research only**: no architecture recommendation, no "use framework X" verdict, no application code. It exists to give the human decision-maker concrete, cited implementation patterns to draw on in later grilling sessions on framework choice, cascade pipeline architecture, provider abstraction design, and latency instrumentation.

**Method note on sourcing:** For every project below, the load-bearing claims (interface shapes, method signatures, class hierarchies) were pulled by fetching the actual source file from `raw.githubusercontent.com` (or the GitHub Contents API for directory structure), not from blog posts. The fetch tool available in this session summarizes fetched content through a small extraction model rather than returning raw text verbatim, so most quotes below are close paraphrase/extraction of real code rather than copy-pasted diffs — but the file paths cited are real, current files in each repo, fetched directly, and several literal code fragments (e.g. the OpenAI WebRTC connection lines, the ephemeral-token endpoint body) came back as verbatim snippets. Where a claim rests on a blog post, docs page, or GitHub issue thread rather than source code, that is called out explicitly. Where something could not be independently confirmed, it's flagged **[secondary]**.

## 1. Pipecat (`github.com/pipecat-ai/pipecat`)

Pipecat is the most directly relevant cascade framework: it is explicitly a frame-based pipeline for STT→LLM→TTS-shaped voice agents, with a large first-party provider ecosystem and (unusually for this space) built-in latency tracing.

### Frame / pipeline abstraction
The core unit is `Frame`, defined in [`src/pipecat/frames/frames.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/frames/frames.py). Frames are typed dataclass-like objects that fall into families:
- **Audio data frames**: `InputAudioRawFrame` / `OutputAudioRawFrame` (transport-facing raw PCM), `UserAudioRawFrame` (per-user tagged input), `TTSAudioRawFrame` (TTS-produced audio tagged with a `context_id`).
- **Text/transcription frames**: `TextFrame`, `LLMTextFrame`, `TranscriptionFrame` (final STT result, carries `user_id`/`timestamp`/`language`), `InterimTranscriptionFrame` (partial STT result), `TTSTextFrame`.
- **Control/system frames**: `StartFrame` (carries sample rates, initializes the pipeline), `EndFrame` (graceful shutdown), `CancelFrame` (immediate stop), `InterruptionFrame` (barge-in trigger), `TTSStartedFrame`/`TTSStoppedFrame` (synthesis boundaries).
- A `UninterruptibleFrame` mixin marks frames (e.g. function-call results) that must survive an interruption/flush.

Frames flow through a graph of `FrameProcessor` objects — [`src/pipecat/processors/frame_processor.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/processors/frame_processor.py). Each processor holds `self._prev`/`self._next` references and routes frames via `push_frame(frame, direction)` where `FrameDirection` is `DOWNSTREAM` (toward output, via `_next`) or `UPSTREAM` (toward input, via `_prev`, used for control/status signaling back up the chain). Internally each processor runs a **dual-queue** design: `SystemFrame`s (start/cancel/interruption) jump a priority queue and are handled immediately, while regular `DataFrame`s are processed in order on a separate queue — this is how Pipecat guarantees an interruption frame can pre-empt a processor that's mid-way through a slow LLM/TTS call without waiting for that call's own queue to drain.

**Interruption handling** lives in `_start_interruption()` on `FrameProcessor`: on receiving `InterruptionFrame`, uninterruptible frames are preserved while everything else queued is flushed, and the processor's own async processing task is cancelled and recreated. This is the single mechanism every downstream service (STT, LLM, TTS) inherits for barge-in — no service reimplements interruption logic itself.

### STT / TTS / LLM service base classes
Provider services live under `src/pipecat/services/` — [`ai_service.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/ai_service.py) (shared base), [`stt_service.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/stt_service.py), [`tts_service.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/tts_service.py), [`llm_service.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/llm_service.py), with 50+ provider subdirectories (Deepgram, Whisper, ElevenLabs, Azure, AWS, Google, etc.) each implementing the same base interface.

`STTService` (`stt_service.py`) exposes a single abstract method:
```python
@abstractmethod
async def run_stt(self, audio: bytes) -> AsyncGenerator[Frame | None, None]: ...
```
i.e. **the swap point between providers is a single async-generator method that takes raw audio bytes and yields Frames.** The base class wraps this in `process_frame()` → `process_audio_frame()` (handles muting, per-user tracking, usage metering) → `process_generator(self.run_stt(...))` which drains the generator and forwards whatever frames it yields. VAD integration is via two frame handlers, `_handle_vad_user_started_speaking()` and `_handle_vad_user_stopped_speaking()`, that reset/start TTFB timers — i.e. VAD is a separate upstream component that emits `VADUserStartedSpeakingFrame`/`VADUserStoppedSpeakingFrame` events which the STT service *observes* rather than computing itself. A `SegmentedSTTService` subclass exists specifically for STT providers (non-streaming) that need VAD to tell them where an utterance boundary is, vs. providers with their own internal streaming VAD.

`TTSService` (`tts_service.py`) mirrors this shape:
```python
@abstractmethod
async def run_tts(self, text: str, context_id: str) -> AsyncGenerator[Frame | None, None]: ...
```
Yielded `None` is a meaningful signal specific to WebSocket-based TTS providers ("more audio is coming asynchronously, keep waiting") vs. HTTP-based providers, which never yield `None` and complete before returning — this is a real, non-obvious swappability wrinkle between provider transport styles that the base class has to paper over. Produced frames are queued per `context_id` via `append_to_audio_context()` and drained in order by a dedicated `_audio_context_task_handler()` task, which is how Pipecat keeps audio ordered even though multiple TTS requests (e.g. sentence-by-sentence) may be in flight. Interruption (`_handle_interruption()`) clears the audio-context queue, calls a provider hook `on_audio_context_interrupted(context_id)`, and stops the drain task.

### Turn-taking / VAD / interruption
The VAD stack is under [`src/pipecat/audio/vad/`](https://github.com/pipecat-ai/pipecat/tree/main/src/pipecat/audio/vad) with a base [`vad_analyzer.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/audio/vad/vad_analyzer.py) and multiple engine implementations (Silero, plus newer AIC/Krisp entries). `VADParams` exposes four tunables: `confidence` (default 0.7), `start_secs`/`stop_secs` (default 0.2s each — minimum sustained speaking/silence before a state transition is confirmed), and `min_volume` (default 0.6). The analyzer runs a 4-state machine — `QUIET → STARTING → SPEAKING → STOPPING → QUIET` — with `start_secs`/`stop_secs` acting as debounce windows so brief glitches don't flip state.

Pipecat also maintains a **separate, model-based "Smart Turn" endpointer** ([`github.com/pipecat-ai/smart-turn`](https://github.com/pipecat-ai/smart-turn)) — a small model that classifies raw waveform (not transcript) for whether an utterance is semantically complete, explicitly because "VAD can't take into account the actual linguistic or acoustic content of speech." It's designed to run **downstream of** a lightweight VAD (Silero), not instead of it: VAD proposes a pause; Smart Turn decides whether that pause is a real end-of-turn. This two-stage design (cheap signal-level gate → more expensive semantic gate) is a reusable pattern independent of Pipecat's specific code.

### Browser/backend transport
`src/pipecat/transports/` has a `base_transport.py`/`base_input.py`/`base_output.py` trio plus per-provider transports, notably [`websocket/`](https://github.com/pipecat-ai/pipecat/tree/main/src/pipecat/transports/websocket) (`server.py`, `client.py`, `fastapi.py` — plain WebSocket audio/data streaming) and [`smallwebrtc/`](https://github.com/pipecat-ai/pipecat/tree/main/src/pipecat/transports/smallwebrtc) (`connection.py`, `transport.py`, `request_handler.py` — a lightweight self-hosted WebRTC transport, as an alternative to their commercial Daily transport, for teams that want WebRTC without a hosted SFU vendor).

On top of transports, Pipecat defines **RTVI** ("Real-Time Voice/Video Inference"), a standardized client↔server JSON message envelope: `{ "id": string, "label": "rtvi-ai", "type": string, "data": unknown }` — documented at [docs.pipecat.ai/client/rtvi-standard](https://docs.pipecat.ai/client/rtvi-standard). This is the thing that lets Pipecat ship one browser SDK ([`pipecat-client-web`](https://github.com/pipecat-ai/pipecat-client-web), packages `@pipecat-ai/client-js` + React bindings `@pipecat-ai/client-react`) that works across all their transports (WebSocket, Daily, SmallWebRTC) — the SDK talks RTVI messages and hands transport specifics to a pluggable `Transport` implementation. The client-react package centers on a `PipecatClient` class plus React hooks/providers for state, device management, and bot messages; server-side authentication/config stays server-side by design ("emphasizes server-side authentication and secret management rather than exposing credentials client-side").

### Audio chunking (text side)
For the LLM→TTS boundary specifically, Pipecat has a dedicated `SentenceAggregator` processor ([`processors/aggregators/sentence.py`](https://reference-server.pipecat.ai/en/stable/api/pipecat.processors.aggregators.sentence.html)) that buffers streaming LLM token deltas and only emits a complete sentence frame once a sentence-ending boundary is detected — trading latency for TTS prosody quality. Docs describe two aggregation modes at the TTS layer: **SENTENCE mode** (buffer to sentence boundary, ~200–300ms added latency, better prosody) and **TOKEN mode** (stream tokens straight to TTS as they arrive, lower latency, quality depends on the TTS provider's own ability to synthesize partial text well) — this SENTENCE-vs-TOKEN tradeoff is explicit, named, and switchable per pipeline.

### Latency instrumentation
This is Pipecat's most directly reusable pattern for this project. Two layers exist:

1. **Built-in per-call metrics** on `FrameProcessor` itself: `start_ttfb_metrics()`/`stop_ttfb_metrics()` (time-to-first-byte per service call), a TTFA (time-to-first-audio) scan that looks for the first audible sample in a stream, and `start_processing_metrics()`/`stop_processing_metrics()` for total processing time — plus usage counters (LLM tokens, STT/TTS characters/seconds). These get pushed downstream as `MetricsData` frames when metrics are enabled on `StartFrame`.
2. **OpenTelemetry tracing**, documented at [docs.pipecat.ai/server/utilities/opentelemetry](https://docs.pipecat.ai/server/utilities/opentelemetry). Traces are hierarchical: **conversation → turn → service span** (`stt`, `llm`, `tts` as children of each `turn` span; for realtime/multimodal services the shape adapts to `llm_setup`/`stt`/`llm_response`/`llm_tool_call` spans instead). Each service span carries `gen_ai.system` (provider), `gen_ai.request.model`, and a `metrics.ttfb` attribute; turn spans carry sequential turn number, duration, and interruption status; conversation spans carry a conversation ID. Enabling it is a few constructor flags — `enable_metrics=True`, `enable_tracing=True`, `enable_turn_tracking=True` on the pipeline runner — and export targets any OTLP-compatible backend (Jaeger, Grafana, Langfuse via OTLP/HTTP, cloud APM vendors, or a console exporter for local debugging).
3. A curated **benchmark reference table** in [`services/stt_latency.py`](https://github.com/pipecat-ai/pipecat/blob/main/src/pipecat/services/stt_latency.py): pre-measured P99 "time-to-final-segment" (speech-end → final transcript) numbers per STT provider (e.g. Deepgram ≈0.35s, OpenAI ≈2.01s), all measured at `VADParams.stop_secs=0.2`, with an explicit note that changing VAD settings invalidates the numbers and you should re-benchmark. This is a small but telling artifact: it shows Pipecat's maintainers treat *STT-specific* latency as a first-class, swap-relevant property of a provider, not an incidental detail — directly relevant to a provider-swappable design that needs comparable per-provider latency data.

A community-maintained companion doc worth flagging as a **concrete numeric example of end-to-end latency budgeting** (not itself a general Pipecat feature, but built on Pipecat) is [`pipecat-ai/nemotron-january-2026/docs/streaming-pipeline-architecture.md`](https://github.com/pipecat-ai/nemotron-january-2026/blob/main/docs/streaming-pipeline-architecture.md), which documents a 500–700ms end-to-end voice-agent pipeline broken into: VAD silence detection ~200ms, STT (NVIDIA Parakeet, 160ms audio chunks) 30–50ms, LLM first segment 100–150ms (a hard 24-token cap on the *first* emitted segment specifically to hit fast TTFB, larger 96-token segments afterward), TTS first audio ~185–370ms (streaming mode for the first segment, batch mode afterward for quality). This is a **turn-based conversational agent's** budget, not a continuous-interpretation one, but it's a rare example of someone publishing real per-stage numbers that sum to a stated end-to-end target — directly useful as a reference point for budgeting the cascade mode's stages, even though it doesn't fit continuous interpretation's shape as-is (see §6).

## 2. LiveKit Agents (`github.com/livekit/agents`)

LiveKit Agents is architecturally the most relevant framework to the specific "cascade AND realtime, provider-swappable" requirement in this ticket, because it is the one project that ships **both** shapes side by side and lets that seam be visible.

### Transport abstraction
[`livekit-agents/livekit/agents/voice/io.py`](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/io.py) defines a **chainable** input/output abstraction independent of any specific STT/TTS/LLM provider or transport:
- `AudioInput(*, label, source: AudioInput | None)` is an async iterator (`__anext__`/`__aiter__`) yielding `rtc.AudioFrame`s, with `on_attached()`/`on_detached()` lifecycle hooks; an optional `source` lets inputs form a chain (e.g. a resampler wrapping a raw mic input).
- `AudioOutput(*, label, capabilities, next_in_chain, sample_rate)` is the sink-side abstract base: `capture_frame(frame)` to push audio out, `flush()` to mark a playback segment complete, `clear_buffer()` for immediate interruption, `pause()`/`resume()`, and `wait_for_playout()` returning a `PlaybackFinishedEvent`. A `replace_audio_tail(sink)` method on `AgentOutput` lets you hot-swap the underlying sink (e.g. switching TTS providers or transports) without breaking any wrapper that was recording/monitoring the stream — done via a stable `_AudioSinkProxy` indirection at the bottom of the chain.
- `AgentInput`/`AgentOutput` coordinate the audio/video/transcription streams as a unit, each with `set_audio_enabled()`/`set_video_enabled()` toggles and change-callbacks.

This is a genuinely reusable pattern for the "transport abstraction" part of this project's provider-swappable requirement: the input/output objects know nothing about WebRTC vs. WebSocket vs. local mic — they're just async-iterable/async-callable frame sources and sinks, and *transports* (LiveKit's `rtc.Room`, in this framework's case) are adapters that produce/consume `AudioInput`/`AudioOutput` instances.

### STT/TTS/LLM plugin interfaces (cascade side)
[`livekit-agents/livekit/agents/stt/stt.py`](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/stt/stt.py) defines the STT provider seam. Two abstract methods: a batch path, `_recognize_impl(buffer: AudioBuffer, *, language, conn_options) -> SpeechEvent`, and a streaming path via a `RecognizeStream` class whose `_run(self) -> None` subclasses implement, with `push_frame(frame)`, `flush()` (mark segment end), `end_input()`, and `__anext__`/`__aiter__` for `async for event in stream: ...` consumption, plus `aclose()`. Results are typed via a `SpeechEventType` enum: `START_OF_SPEECH`, `INTERIM_TRANSCRIPT`, `PREFLIGHT_TRANSCRIPT` (stable-but-revisable), `FINAL_TRANSCRIPT`, `RECOGNITION_USAGE`, `END_OF_SPEECH`. Providers self-declare feature support via a `STTCapabilities` dataclass (`streaming`, `interim_results`, `diarization`, `aligned_transcript: Literal["word","chunk",False]`, `offline_recognize`, `keyterms`, `chat_context`) — i.e. the abstraction is designed around **capability negotiation** rather than assuming every provider supports every feature, which matters for a swappable-provider design where, e.g., not every STT vendor streams interim results the same way.

There are also `fallback_adapter.py` (wraps multiple STT providers with automatic failover), `stream_adapter.py` (adapts a batch-only STT into the streaming interface by internally chunking/re-calling), and `multi_speaker_adapter.py` — these adapter classes are themselves a reusable pattern: rather than every provider re-implementing streaming-over-batch or failover, the base package provides generic wrapper adapters that any provider automatically benefits from.

### RealtimeModel abstraction (realtime side) — and the key finding
[`livekit-agents/livekit/agents/llm/realtime.py`](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/llm/realtime.py) defines `RealtimeModel`/`RealtimeSession` as the seam for realtime speech-to-speech providers (OpenAI Realtime, Gemini Live). `RealtimeModel.session(*, turn_detection_disabled: bool = False) -> RealtimeSession` creates a session; the model exposes `capabilities` (a `RealtimeCapabilities` dataclass advertising things like message truncation support, turn detection, tool automation) so callers can branch on what a given realtime provider actually supports. `RealtimeSession` exposes audio I/O (`push_audio(frame)`, `push_video(frame)`, `commit_audio()`, `clear_audio()`), generation control (`generate_reply(...)`, `interrupt()`, `truncate(...)`), and context mutation (`update_instructions()`, `update_chat_ctx()`, `update_tools()`), all surfaced as typed events (`input_speech_started`, `generation_created`, `metrics_collected`, etc.) via an `EventEmitter`.

**The important finding for this project's provider-abstraction question:** LiveKit Agents does **not** unify the cascade STT/LLM/TTS interfaces with the RealtimeModel interface under one shared "transport" abstraction. They're deliberately separate object families — `STT`/`TTS`/`LLM` model discrete transcription/generation/synthesis steps; `RealtimeModel`/`RealtimeSession` models an end-to-end speech-in/speech-out system with its own event vocabulary, and a `MessageGeneration` result carries both a `text_stream` and an `audio_stream` simultaneously because the provider generates speech directly rather than through a separate TTS call. `AgentSession` (the orchestrator, `livekit-agents/livekit/agents/voice/agent_session.py`) is what can be configured with *either* a cascade (`stt=`, `llm=`, `tts=`) or a realtime model (`llm=<RealtimeModel instance>`), but the two paths are genuinely different code paths underneath, not one interface with two implementations. This is directly relevant evidence against trying to force cascade-mode and realtime-mode into one identical provider interface in this project — a mature, widely-used framework explicitly chose *not* to do that, and instead shares only the outer transport (`AudioInput`/`AudioOutput`) and orchestration (`AgentSession`) layers.

### Turn-taking / endpointing
[`livekit-agents/livekit/agents/voice/endpointing.py`](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/endpointing.py) implements **silence-duration-based** endpointing (not semantic), with two strategies: `BaseEndpointing` (fixed `min_delay`/`max_delay`) and `DynamicEndpointing`, which adaptively *learns* a per-user minimum pause threshold from observed behavior — it distinguishes an intra-utterance pause (user pausing mid-thought) from a real end-of-turn by tracking historical pause durations with an exponential moving average (`alpha=0.9` default) and adjusting `min_delay` between a floor and a fixed `max_delay` ceiling. A `create_endpointing()` factory selects `"dynamic"` vs `"fixed"` mode. There's also a separate `agent_activity.py` (199KB — the largest file in the voice module) that appears to own the broader interruption/turn state machine, and `audio_recognition.py` for pairing STT output with endpointing decisions; these weren't read in full but are worth flagging as the deeper implementation if the human wants to go further.

### Translation-specific examples
This is the most valuable find for the "is there anything purpose-built for continuous interpretation, not turn-based dialogue" question:
- **[`livekit-examples/live-translated-captioning`](https://github.com/livekit-examples/live-translated-captioning)** — an agent that subscribes to one host's mic stream continuously (no turn boundary needed because the output is *text captions*, not spoken audio, so there's nothing to "interrupt"), runs Deepgram STT, pipes each transcription through a custom `Translator` component calling GPT-4o per-language, and broadcasts both source and translated captions to listeners via an `STTForwarder`-based fan-out keyed by each listener's language preference. Notably, **because output is text not speech, this sidesteps the entire turn-taking/barge-in problem** that a spoken interpretation output would face — it's evidence that "continuous streaming translation" and "turn-based voice agent" are different enough problems that even LiveKit's own example repo picks a text-output shape to avoid the turn-taking mismatch, rather than solving it for spoken output.
- **[`livekit-examples/gemini-live-translate`](https://github.com/livekit-examples/gemini-live-translate)** — closer to a full spoken-interpretation shape: one Gemini Live session is spun up **per (speaker, target-language) pair** on demand (when Bob sets `attributes.lang = "es"` and Alice speaks, a session translating Alice→Spanish is created), publishing a translated audio track named `tx:<speaker>:<lang>` plus `lk.translation` captions. A Python `TranslationRouter` runs a **reconciliation loop**: it watches `participantAttributesChanged` events, maintains a demand-set of active `(speaker, target_lang)` pairs, **debounces reconciliation by 250ms** (so rapid attribute changes / speech don't thrash session creation), and applies a **10-second grace period** on mute so a brief pause doesn't tear down and rebuild the session. Same-language pairs are explicitly bypassed to save cost. Source layout: `translator/src/agent.py` (entry point via `@server.rtc_session()`), `router.py` (the reconciliation logic), `session.py` (one `GeminiSession` per speaker→target pair), `audio.py` (16kHz-in/24kHz-out PCM handling). **This demand-driven, per-pair-session, debounced-reconciliation pattern is the single most directly transferable "continuous interpretation, not turn-based dialogue" architecture pattern found in this research** — it solves the real problem (translate one continuous stream, without discrete conversational turns, while tolerating natural pauses) rather than working around it.
- **[docs.livekit.io/recipes/pipeline_translator](https://docs.livekit.io/recipes/pipeline_translator/)** — a simpler recipe: English STT → LLM translation → French TTS, explicitly built from LiveKit's cascade plugin primitives (not `AgentSession` defaults) to show the seams. Framed as "listen in English, translate with an LLM, speak the result in French" — this reads as turn-based/utterance-based rather than continuously overlapping, i.e. it's a cascade-pipeline-composition example more than a turn-taking-model example.
- **[GitHub issue #3860](https://github.com/livekit/agents/issues/3860)**, "Real-time translation agent using LiveKit Agent without turn detection" — a still-open (unassigned, unresolved at research time) feature request that states the problem plainly: LiveKit's default `AgentSession` pipeline is "turn-based, and the audio is processed only after a speech segment is detected and closed by VAD," which the requester says introduces unacceptable delay for simultaneous interpretation; they explicitly ask whether `AgentSession`/`RealtimeModel` can be driven in "a streaming loop, without waiting for turn completion," or whether they need to drop to the lower-level `AudioStream` primitives directly. **No maintainer response or workaround is recorded in the thread.** This is useful negative evidence: even in a framework whose maintainers actively ship translation examples, "true continuous/simultaneous interpretation without turn boundaries" is an acknowledged, currently-unsolved gap in the high-level API — which validates that this project's brief (build both modes, and think hard about the cascade turn-taking shape) is pointing at a real, not yet fully solved, problem.

## 3. OpenAI reference implementations

### `openai-realtime-console` — the canonical WebRTC + ephemeral-token example
Repo: [`github.com/openai/openai-realtime-console`](https://github.com/openai/openai-realtime-console). Structure: an Express backend (`server.js`) plus a Vite/React frontend (`client/`), with components `App.jsx`, `Button.jsx`, `EventLog.jsx`, `SessionControls.jsx`, `ToolPanel.jsx`.

**Ephemeral token minting**, in [`server.js`](https://github.com/openai/openai-realtime-console/blob/main/server.js): the backend's `GET /token` route does a server-to-server `POST https://api.openai.com/v1/realtime/client_secrets` with `Authorization: Bearer <standard API key>` and a body pre-configuring the session:
```json
{
  "session": {
    "type": "realtime",
    "model": "gpt-realtime",
    "audio": { "output": { "voice": "marin" } }
  }
}
```
and forwards OpenAI's response (containing the short-lived client secret) straight to the browser. A second, experimental `POST /session` route accepts a raw SDP offer from the browser and relays it server-side to `https://api.openai.com/v1/realtime/calls` — i.e. the repo actually demonstrates **both** of the two connection patterns (ephemeral-token-then-direct, and full SDP relay) mentioned in this project's companion research doc on Realtime API integration.

**Browser-side WebRTC connection**, in [`client/components/App.jsx`](https://github.com/openai/openai-realtime-console/blob/main/client/components/App.jsx) — the actual sequence, in order:
1. `fetch("/token")` → extract `EPHEMERAL_KEY` from the response.
2. `const pc = new RTCPeerConnection();`
3. `pc.ontrack = (e) => (audioElement.current.srcObject = e.streams[0]);` — remote (model) audio is played by assigning the incoming track's stream directly to an `<audio>` element's `srcObject`, no manual buffering/decoding needed.
4. `const ms = await navigator.mediaDevices.getUserMedia({ audio: true }); pc.addTrack(ms.getTracks()[0]);` — local mic track added to the peer connection.
5. `const dc = pc.createDataChannel("oai-events");` — a literally-named `"oai-events"` data channel carries the JSON realtime event protocol (session updates, transcript deltas, function calls) alongside the raw audio tracks.
6. `pc.createOffer()` → `pc.setLocalDescription(offer)` → POST the SDP to `https://api.openai.com/v1/realtime/calls?model=gpt-realtime` with the ephemeral bearer token → set the returned SDP as the remote description.

**React state pattern**: three pieces of state carry the whole session — a boolean `isSessionActive` (flipped true on the data channel's `"open"` event), an `events` array accumulated via `setEvents((prev) => [message, ...prev])` on every data-channel message (used to drive the `EventLog` UI), and a `dataChannel` ref used to send outbound JSON events. This is a minimal, un-opinionated state shape — no external state library, just `useState`/`useRef`/`useEffect` wiring peer-connection lifecycle events to component state. For a project that needs comparable session-lifecycle state (connecting/connected/error, transcript log, current turn) this is a legitimate minimal reference for "how little state machinery you actually need" before reaching for something heavier.

### `openai-realtime-agents` — agentic patterns on top of Realtime
[`github.com/openai/openai-realtime-agents`](https://github.com/openai/openai-realtime-agents) demonstrates two orchestration patterns on top of a single long-lived Realtime connection: **sequential handoff** (multiple specialist agents, each with its own instructions/tools, and the model itself decides when to hand off via a tool call — a handoff triggers a `session.update` event that swaps in new instructions/tools without tearing down the connection) and **chat-supervisor** (a fast realtime "front" agent handles basic turns, deferring complex tool calls to a slower text-only supervisor model like GPT-4.1). Not directly about translation, but the **`session.update`-to-swap-instructions-mid-connection** mechanic is relevant if this project ever needs to change target language or interpretation mode without dropping the WebRTC session — it's evidence that Realtime sessions are designed to be reconfigured live rather than recreated per change. **[secondary — summarized from README/search, not independently read at the source-diff level]**.

### `gpt-realtime-translate` — OpenAI's own purpose-built continuous-translation model
Documented in [`openai-cookbook/examples/voice_solutions/realtime_translation_guide.mdx`](https://github.com/openai/openai-cookbook/blob/main/examples/voice_solutions/realtime_translation_guide.mdx), with companion demo scaffolds at `.../realtime_translation_guide/{browser-translation-demo,twilio-translation-demo,livekit-translation-demo}` (at research time, the `browser-translation-demo` folder had README/Dockerfile/package.json checked in but empty `src/`/`test/`/`scripts/` directories — i.e. **the code is not actually present in the repo**, only the scaffold and the guide's inline snippets; treat this as a documented pattern, not a runnable reference implementation). This is the single clearest piece of evidence in this research for "what does purpose-built continuous interpretation actually look like, architecturally, as opposed to a conversational voice agent":
- **No turn boundary at all.** The guide states outright: "there is no `response.create`, assistant turn, tool call, or conversation state to manage." Audio flows bidirectionally and continuously — including silence — and the model emits ~200ms translated-audio chunks plus streaming transcript deltas as it goes, rather than waiting for a VAD-detected end-of-turn before starting to speak.
- **Structured language targeting** instead of prompt engineering: session config sets `audio.output.language` (e.g. `"es"`) directly; source language is auto-detected from the incoming audio. No `instructions`/system-prompt field is exposed at all for this model — OpenAI's framing is that the model's "interpreter" role is fixed by training, not steerable.
- **Purpose-trained for restraint**: the guide notes it was trained on "thousands of hours of professional interpreter audio" specifically to keep it from turning into a chatty conversational assistant and to make it "wait for enough context before producing speech" — i.e. the provider baked a translation-appropriate pacing/latency-vs-completeness tradeoff into the model itself rather than leaving it to client-side turn-detection tuning.
- **Voice is not selected** — output speech "follows the source speaker's general tone, pitch, and speaking style" dynamically, unlike conversational Realtime sessions where you pick a fixed voice.
- Three deployment shapes are documented, each a different transport pattern: (1) **browser tab audio** via `getDisplayMedia()` + direct WebRTC to the translation endpoint; (2) **Twilio phone bridge**, converting 8kHz μ-law ↔ 24kHz PCM16 and bridging through a translation session server-side; (3) **LiveKit video rooms**, where a per-remote-participant "translation sidecar" subscribes to their mic track over WebRTC and plays translated audio locally without republishing into the room (avoiding an echo/rebroadcast loop). This third shape is architecturally close to the LiveKit `gemini-live-translate` per-speaker-session pattern above, despite using a different underlying model — suggesting "one translation session per source speaker, subscribed directly to their track" is a converging pattern across at least two independent implementations (OpenAI's own cookbook, and LiveKit's example repo).

This confirms something worth surfacing directly to the human: **OpenAI itself treats "conversational realtime agent" and "continuous interpreter" as different enough problems to ship a structurally different model and a structurally different session protocol** (no `response.create`, no instructions field, native dual-transcript-delta streams) rather than just prompt-steering the general `gpt-realtime` model. That's strong outside validation for why this project's brief calls for building two genuinely distinct modes/mental models rather than one flexible pipeline.

## 4. Vocode (`vocodedev/vocode-core`, formerly `vocode-python`)

The project renamed from `vocode-python` to `vocode-core`; the modular provider-abstraction structure the ticket asked about is intact. Repo: [`github.com/vocodedev/vocode-core`](https://github.com/vocodedev/vocode-core).

**Transcriber abstraction** — [`vocode/streaming/transcriber/base_transcriber.py`](https://github.com/vocodedev/vocode-core/blob/main/vocode/streaming/transcriber/base_transcriber.py): `AbstractTranscriber` declares one abstract method, `async def _run_loop(self)`, that each provider implements however it needs to. Audio comes in via `send_audio(chunk: bytes)`, which — notably — **substitutes a silent chunk of the same length when muted** (`self.consume_nonblocking(self.create_silent_chunk(len(chunk)))`) rather than dropping input, presumably to keep whatever internal frame/timing accounting the provider does intact. Results go out via `produce_nonblocking(item: Transcription)` to a generic `consumer: AbstractWorker[Transcription]`. There's no endpointing config on the base class itself — that logic lives inside each provider's `_run_loop()` implementation, meaning Vocode's abstraction is thinner/more provider-delegated here than Pipecat's (which centralizes VAD state-machine logic in one shared analyzer).

**Synthesizer abstraction** — [`vocode/streaming/synthesizer/base_synthesizer.py`](https://github.com/vocodedev/vocode-core/blob/main/vocode/streaming/synthesizer/base_synthesizer.py): `BaseSynthesizer.create_speech_uncached(message, chunk_size, is_first_text_chunk, is_sole_text_chunk) -> SynthesisResult`. `SynthesisResult` wraps an `AsyncGenerator[ChunkResult, None]` (each `ChunkResult` is `(chunk: bytes, is_last_chunk: bool)`) plus a `get_message_up_to(seconds)` callback that lets the caller ask "how much of the source text corresponds to audio played up to time T" — useful for accurately reporting what was actually said if playback is interrupted mid-sentence. Class-level `get_cost()`/`get_voice_identifier()` hooks exist for cost accounting and caching keys per provider.

**Turn-taking / interruption**, in [`streaming_conversation.py`](https://github.com/vocodedev/vocode-core/blob/main/vocode/streaming/streaming_conversation.py): this is a squarely **turn-based, conversational** design, useful mainly as a *contrast* case for this project. A `TranscriptionsWorker` treats `transcription.is_final == True` as the turn-completion signal (tracking `is_human_speaking = not transcription.is_final`) and only then triggers the agent/LLM response. Barge-in is handled by `broadcast_interrupt()`, called when the human starts speaking while `is_human_speaking` was already false (i.e. bot was talking): it drains the interruptible-event queue, cancels pending synthesis/output tasks, and calls `output_device.interrupt()`. Notably, Vocode explicitly **filters backchannel utterances** ("mhm", "yeah", regex-matched) so they don't trigger a false interruption — they're buffered into the transcript instead of cutting off the bot. Audio playback streams `SynthesisResult` chunks wrapped in `InterruptibleEvent` objects so an in-flight chunk can be aborted mid-stream. **None of this — is_final-triggered turns, backchannel suppression, single-active-speaker interruption — maps onto a continuous-interpretation use case**, where there generally isn't a "turn" to complete and no bot speech to be interrupted by backchannels; it's included here specifically so the contrast is visible and citable rather than assumed.

## 5. Purpose-built continuous speech-translation / interpretation prior art

This section directly targets the ticket's ask to find something closer to "continuous streaming translation of one speaker's ongoing speech" rather than turn-based dialogue.

- **Hugging Face `speech-to-speech`** ([`github.com/huggingface/speech-to-speech`](https://github.com/huggingface/speech-to-speech)) — an open, modular cascaded pipeline (VAD → STT → LLM → TTS) built entirely on Transformers-hub models. Architecturally distinctive: it's **queue-and-thread based rather than frame-processor-graph based**. [`src/speech_to_speech/s2s_pipeline.py`](https://github.com/huggingface/speech-to-speech/blob/main/src/speech_to_speech/s2s_pipeline.py) wires stages together with plain `Queue` objects — `recv_audio_chunks_queue → spoken_prompt_queue → stt_output_queue → text_prompt_queue → lm_response_queue → lm_processed_queue → send_audio_chunks_queue` — and runs each stage handler on its own Python thread via a `ThreadManager`, with a shared `stop_event` for coordinated shutdown. Every stage handler subclasses [`baseHandler.py`](https://github.com/huggingface/speech-to-speech/blob/main/src/speech_to_speech/baseHandler.py)'s `BaseHandler`, whose only required override is `process(input) -> Iterator[output]` (a **generator**, not an async generator — this is thread-based concurrency, not asyncio) plus optional `setup()`/`cleanup()`/`should_process_input()`/`should_emit_output()` hooks; the base `run()` loop blocks on `queue_in.get(timeout=0.1)`, checks for `SESSION_END`/`PIPELINE_END` sentinels, iterates the handler's `process()` generator, and forwards each output. This is a legitimate, much simpler alternative pattern to Pipecat's async frame-processor graph — a straight-line pipeline of blocking-generator stages connected by queues — worth naming explicitly as an alternative shape for the cascade mode, not just Pipecat's shape. It is however still a **turn-based conversational** cascade (it's an "S2S" chat model pipeline, not built for continuous overlapping interpretation) — the queue/thread wiring pattern transfers, the turn semantics don't.

- **`livekit-examples/live-translated-captioning`** and **`livekit-examples/gemini-live-translate`** — covered in depth in §2 above; these remain the two strongest "actually continuous, not turn-based" examples found, precisely because both sidestep the turn-completion problem in different ways (captioning avoids spoken-output interruption entirely; per-speaker Gemini sessions with debounced reconciliation and a mute grace period handle continuous speech without an explicit turn state machine).

- **OpenAI's `gpt-realtime-translate`** — covered in §3 — is the clearest *model-level* commitment to "no turn boundary, continuous stream in, continuous stream out."

- **Meta `seamless_communication` / SeamlessStreaming** ([`github.com/facebookresearch/seamless_communication`](https://github.com/facebookresearch/seamless_communication)) — a research-grade streaming speech-to-speech/speech-to-text translation model family (2.5B-parameter `SeamlessStreaming`, monotonic-decoder + streaming UnitY2 checkpoints). This is **not an application reference implementation** the way the others are — it's closer to a model + inference library than a pipeline you'd deploy as-is — but it's worth naming because its whole reason for existing is a genuinely different **chunking policy** from VAD-triggered segmenting: streaming simultaneous-translation models like this typically process audio in small fixed windows with a monotonic decoding policy deciding, per window, whether it has enough context to commit to more output yet or must wait for more input — i.e. chunking driven by a learned "read vs. write" policy rather than by silence detection. **[secondary — repository README/description level only; the streaming policy internals were not read at the source-code level in this pass, so treat the chunking-policy characterization as informed inference from the model's documented design, not a verified code citation]**. Flagging this mainly so the human knows this alternate chunking philosophy (context-window-and-policy-driven vs. VAD-silence-driven) exists in the literature, even though it's out of reach for a take-home project's timeline.

- **`pipecat-ai/pipecat` issue #1747**, ["Meeting translation pipeline suggestion"](https://github.com/pipecat-ai/pipecat/issues/1747) — a real user hitting exactly the shape of problem this project has to solve: they want continuous bilingual (French↔English) meeting translation and lay out the tradeoff directly — "If I use STT + LLM + TTS, it is easy, because STT can autodetect the [spoken] language and give it on [the] Transcribe Frame, but it is time and token cost," versus using a dedicated speech-to-text-translation service (faster/cheaper) which requires knowing source/target language *in advance*, which is awkward for a bilingual (not fixed-direction) conversation. The issue is closed with no documented resolution or maintainer architectural guidance visible. This is useful **negative evidence** again: language-direction ambiguity in a continuous, not-strictly-turn-taking, possibly-bidirectional interpretation scenario is a live, unresolved friction point even for people building directly on the most mature cascade framework in this space — worth the human knowing this isn't a solved problem they're missing an obvious answer to.

## Implications for this project

Mapped explicitly to the four open decisions this research feeds. These are observations about what exists, not recommendations — the framing below deliberately separates "reusable pattern" from "doesn't fit, here's why," per the ticket's instruction not to steer the design.

### Framework choice
- No survey result changes the brief's implicit expectation that this project **hand-builds** its own thin pipeline rather than adopting Pipecat or LiveKit Agents wholesale — and the research itself supports why: LiveKit's own open issue (#3860) and Pipecat's own open issue (#1747) show that *neither* framework has a finished, idiomatic answer for "continuous interpretation, not turn-based dialogue" today. Adopting either wholesale would mean fighting the framework's turn-taking assumptions rather than being helped by them.
- What's genuinely reusable as *reference*, not as dependency: Pipecat's frame/`FrameProcessor` vocabulary (data frames vs. system frames vs. control frames, `push_frame(direction)`) is a clean, minimal design worth studying even if reimplemented from scratch in TypeScript for a browser SPA. LiveKit's separation of transport (`AudioInput`/`AudioOutput`) from provider (`STT`/`TTS`/`LLM`) from orchestration (`AgentSession`) is a clean layering to imitate at a conceptual level.
- HuggingFace `speech-to-speech`'s queue+thread pipeline is evidence that a much simpler, non-async-framework shape (plain queues + generator-based stage handlers) is a legitimate, working alternative to a Pipecat-style async frame graph — useful if the human wants to keep the cascade-mode implementation intentionally simple rather than build a mini frame-processor framework.

### Cascade pipeline architecture (turn-taking / chunking)
- The clearest, most load-bearing finding: **turn-based endpointing (VAD-silence → STT finalize → LLM respond → TTS speak → wait for next turn) is the pattern in Pipecat, LiveKit's default `AgentSession`, and Vocode — and it is explicitly the wrong shape for continuous interpretation**, per both the LiveKit and Pipecat community threads cited above and per OpenAI's own architectural choice to ship a *different, turn-free* session protocol for `gpt-realtime-translate`.
- The two most directly transferable continuous-shape patterns found: (1) LiveKit's `gemini-live-translate` demand-driven per-(speaker,target-language) session with debounced reconciliation (250ms) and a mute grace period (10s) — this is a real, working answer to "how do you run continuous translation without a turn state machine," worth studying at the `router.py`/`session.py` level if the human wants to go deeper than this summary; (2) the general shape shared by OpenAI's `gpt-realtime-translate` and the LiveKit "translation sidecar" pattern — one persistent translation stream per source speaker, fed continuously, with no `response.create`/explicit-turn equivalent.
- Pipecat's two-stage VAD → Smart-Turn endpointing (cheap signal gate, then a semantic-completeness model) is a reusable *idea* independent of whether the human keeps any Pipecat code: cheap continuous chunk boundary detection (e.g. every N ms or on a short VAD pause) feeding a translation-unit decision, separate from any "has the whole thought finished" judgment — which for continuous interpretation may not even be needed the way it is for a reply-generating agent.
- Text-side chunking (Pipecat's SENTENCE-vs-TOKEN TTS aggregation mode) is a directly relevant, honestly-named tradeoff for the cascade mode's translation→TTS boundary specifically, independent of the turn-taking question.

### Provider abstraction interface design
- Consistent shape across Pipecat (`run_stt(audio) -> AsyncGenerator[Frame]`, `run_tts(text, context_id) -> AsyncGenerator[Frame]`), LiveKit (`RecognizeStream`/async-iterator-of-`SpeechEvent`, `STTCapabilities` for feature negotiation), and Vocode (`_run_loop`, generator-based `SynthesisResult`): **the swap point that keeps recurring, independent of framework, is "one streaming method, in: raw input; out: an async stream of typed events/frames."** That convergence across three independently-built systems is worth weighting as a real signal, not just one framework's opinion.
- LiveKit's `STTCapabilities`/`RealtimeCapabilities` pattern (a small dataclass a provider fills in to declare what it actually supports, checked by callers before use) is a lightweight way to keep a provider interface swappable without every provider needing to support every feature identically — directly useful if e.g. not every STT/TTS vendor evaluated for this project streams interim results or word-level timing the same way.
- **The clearest negative/contrast finding for this decision**: LiveKit deliberately keeps the cascade (`STT`/`LLM`/`TTS`) interface family and the realtime (`RealtimeModel`/`RealtimeSession`) interface family **separate**, sharing only the outer transport and orchestrator layers. A mature framework built by people who support both modes chose not to force them into one unified provider interface. That's a fact this project's provider-abstraction design should weigh directly — a unified interface across "cascade STT/TTS provider" and "realtime speech-to-speech provider" is not something any of the surveyed prior art actually does, even where it would have been convenient to claim.
- Vocode's `send_audio()` silent-chunk-substitution-on-mute and its `get_message_up_to(seconds)` callback (report how much of the source text was actually spoken before an interruption) are small, specific, genuinely reusable ideas independent of the broader turn-based/interruption-heavy design they live in.

### Latency instrumentation design
- Pipecat's OpenTelemetry span hierarchy (conversation → turn → per-service span, each service span carrying provider/model identity and a `ttfb` attribute) is the most complete, working prior-art example of exactly the "per-stage latency instrumentation" this project's brief asks for, and it's protocol-based (OTLP) rather than bespoke, so it's a reasonable structural reference even without adopting Pipecat's code. **Caveat**: it's built around a *turn* as the unit of aggregation — this project would need an equivalent unit for continuous interpretation (e.g. a translation-chunk or utterance-window ID instead of a "turn").
- The `nemotron-january-2026` streaming-pipeline-architecture doc's numeric per-stage budget (VAD ~200ms + STT 30–50ms + LLM-first-segment 100–150ms + TTS-first-audio ~185–370ms ≈ 500–700ms total) is the one concrete example found of someone publishing a real stage-by-stage budget that sums to a stated target — useful as a structural template (stage → measured contribution → running total vs. target) for this project's own <2s/<1.5s budgeting, even though the actual numbers come from a turn-based agent on specific hardware/models and shouldn't be reused as-is.
- Pipecat's `stt_latency.py` benchmark table (pre-measured P99 TTFS per STT provider, tied to a specific VAD `stop_secs` setting, with an explicit "re-benchmark if you change VAD settings" caveat) is a small but concrete pattern for how to keep per-provider latency data honest in a swappable-provider system: latency numbers are provider-*and*-configuration pairs, not provider-alone constants.
- Nothing surveyed instruments latency specifically for a *continuous, turn-free* pipeline — every latency-instrumentation example found (Pipecat's tracing, the nemotron doc) assumes a turn or a discrete request/response as the unit of measurement. This is a real gap the human will need to design past, not something prior art hands over ready-made.

### Honest summary of fit
Reusable near-directly, regardless of continuous-vs-turn-based: the streaming-async-generator provider interface shape; capability-declaration dataclasses; conversation/turn/service-style hierarchical tracing (with "turn" redefined); OTLP as an export protocol; SENTENCE-vs-TOKEN-style named tradeoffs at pipeline boundaries; ephemeral-token + direct WebRTC as the browser-realtime connection pattern (this part transfers untouched, since it's provider-protocol-level, not turn-taking-level).

Specific to conversational agents and **not** a fit for continuous interpretation as-is: VAD-silence-triggers-turn-completion as the primary chunking mechanism (Pipecat, LiveKit default, Vocode all share this and it's the thing multiple GitHub issues flag as wrong for interpretation); backchannel-suppression/single-speaker-interruption logic (Vocode); `is_final`-transcript-triggers-agent-response as the pipeline's forward-motion signal; and any framework's default `AgentSession`/`StreamingConversation`-level orchestration, which is built around "wait for a turn, generate one reply, speak it, wait again" rather than a continuously flowing translation stream.
